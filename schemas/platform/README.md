# schemas/platform

| Schema | What |
|---|---|
| `model_roles.json` (1.2) | alias table: `mdl:<alias>` -> tier + bindings (`svc:` backend, model id) + fallback. Consumers name only the alias. 1.2 adds a per-binding pin (`version`, `digest: sha256:<hex>`; `hnx golden pins check` requires both and a current evaluation report, G-11) and per-role `limits` (requests, tokens, cost per window; `homelabnext.registry.limits`, G-10) |
| `model_store.schema.json` (1.0) | the one model store (ADR-0023): each model once per (source, revision, quant), `format` hf / gguf / export, the pinned 40-hex source commit, every file's sha256 and size, licence, the engines that may serve it; an entry's digest (sha256 of its `sha256sum` listing) is what a role binding pins. Semantic rules in `homelabnext.models.store` (`hnx models store validate|check`) |
| `model_serving.schema.json` (1.0) | the serving spec: per `svc:` backend the engine (vllm, llama-server), port, GPUs, parallelism and extra engine flags; joined with the store and the role table by `homelabnext.models.serving` into the `vllm_server` role's instances and the gateway's local backends (`hnx models serving render|check`) |
| `mcp_server.schema.json` (1.1) | one MCP catalog record (ADR-0024, docs/mcp-catalog.md): id, owner, pinned origin (first-party path, package with exact version and sha256 or lock, image digest, git commit), transport (stdio command, or streamable-http/sse by `svc:` registry name), runtime, `secret:` env and headers, settings, typed per-instance parameters and the instance name template, egress, data tier, the capabilities it fronts and the contracts it implements, every tool with its capability classes and approval, review and lifecycle. 1.1 adds `acts_via` (`broker`: only the broker's own front, whose tools are broker calls; `direct`: an exception, with `direct_reason`), the tool class `send`, and says that only the broker grants an approval (ADR-0030). Semantic rules in `homelabnext.mcp.servers` (`hnx mcp catalog check`) |
| `module.schema.json` (1.0, **draft**) | one provider, feature or core module (ADR-0027, proposed; docs/modules.md). A draft (`x-draft`): no frozen baseline, may change until a loader and the pilot exist; generated by `python -m homelabnext.schemas` (its examples and negatives too). `manifest_version`; `kind` provider (one product; `provides.slots` keyed by slot, each with adapter, formats, conformance target or provisional reason, migration only for stateful slots; licence, credentials with a `holder`, control plane), feature (interfaces, bundle) or core (`core-*`, never removed: staff agents, core consumers); owned `interfaces`; `requires`/`prefers` with fallbacks that move data; hosts with footprints over cpu, memory, disk and GPU and exposure `isolated`; `egress`; `contributes` (never authority); owned `data`; `config`; `lifecycle`; `origin`. Loader rules in docs/modules.md; contract tests in `tests/schemas/test_module_1_0.py` |
| `module_swap.schema.json` (1.0, **draft**) | the module-keyed part of swap record 1.2 (ADR-0027, proposed; docs/modules.md, "Swap record 1.2"): the outgoing and incoming provider modules and the slot instances that move, the route as an endpoint or a selection diff, cutover legs, the dependants report that gates the cutover, meaning changes, migration evidence or a start-empty decision, revoked credentials; semantic rules in `homelabnext.modules.swap` |
| `module_lock.schema.json` (1.0, **draft**) | the overlay's `lab/modules.lock` (ADR-0027 follow-up 5; docs/modules.md, "Supply chain"): per fetched module its origin (the manifest's), tree digest and the reviews of that tree; in-tree modules are never locked; rules in `homelabnext.modules.supply` |
| `export_manifest.schema.json` (1.0, **draft**) | what a stateful slot's export wrote and its `import_` is held to (ADR-0027 follow-up 7; docs/modules.md, "Import validation"): the slot, the export format, every file's path, size and sha256, and the totals; the rules a schema cannot state (case-insensitive uniqueness, no file under a file, totals equal to the sums, the importer's limits, the tree itself) in `homelabnext.modules.importcheck` |
| `lake_table.schema.json` (1.0, **draft**) | one lake table's declaration (owner, schema, retention, maintenance, freshness), promoted from the manifest's inline lake tables; modules and the core declare tables the same way (ADR-0027) |
| `capability.schema.json` | descriptor for a `cap:` seam: layer 1..13, contract `$id`s, conformance path, readiness flags, implementations |
| `role_interface.schema.json` | what a deployable role provides/requires, its `svc:` id and the five hooks `deploy health readiness backup export` (tags + idempotency); UTC-only schedules |
| `agent_profile.schema.json` | compiled least-privilege agent profile (1.1 declares `reads_untrusted`; a policy that marks the profile a reader overrides `false`); `mcp` must be a subset of `mcp_ceiling` (`check_profile_ceiling`); model is a role alias; hard budgets |
| `broker_action.schema.json` | one allowlisted broker action (default deny); `execute`/`privileged` tiers require approval; audit always on |
| `site.schema.json` | the site/network model: zones (VLAN, subnet, DHCP, egress), router and switches, firewall policy between zones, DNS; secrets and endpoints by reference only (`secret:`, `svc:`); 1.1 adds `power` (the UPSes and a default declaration), the `edge` uplink chain and a `power` declaration on the router, switches and edge devices (`homelabnext/power.py`); 1.2 adds `tailnet.deploy` (the CI deploy tag's tailnet access: SSH to listed zones, other ports only with a reason; `homelabnext/tailnet.py`); 1.3 adds the `mirror` port kind and `mirror_from` (a SPAN destination for a network sensor). Consumed by `homelabnext.network` |
| `guest.schema.json` | one guest (VM, container or host): `guest:` id, placement, resources, image, cloud-init, network zone and address, `cap:` capability, backup policy, lifecycle; 1.3 adds `baseline` (named defense baselines, per-guest `add`/`remove`, or a documented `exemption`). 1.4 adds `status` (planned, live, retired), a one-line `description` and, for a `kind: host`, `power` (the UPS that feeds it). Consumed by `homelabnext.compute` |
| `baseline_set.schema.json` | the guest baseline set (`_baselines.yml` beside the guest files, ADR-0016): a catalogue of product-neutral defense `controls` (one layer each of identity, host, network, detection, data, recovery; a `verify` observable; the Ansible `role` that implements it, `null` until a product is chosen) and named `baselines` of controls that may `extends` others; 1.1 adds a control's `apply` (`guest`, or `central` on the product host's `group`, ADR-0016 decision 7). Consumed by `homelabnext.compute.baselines` |
| `customization.schema.json` | a lab or vendor customization: kind (profile, patch-overlay, role override, hook, registry patch), scope as logical ids, mandatory `reason`, `owner`, `review_by` and `upstream` status. Consumed by `homelabnext.customization` and invariant X-09 |
| `swap_record.schema.json` | the persisted state of one capability swap: nine procedure steps with gates and evidence, hash-chained transition log, route before/after the flip, rollback or closure. Written by `hnx swap`; semantic checks in `homelabnext.swap.record` |
| `script_header.schema.json` | the `# hnx-script:` header every script carries: id, kind (`check`, `tool`, `job`, `service`), purpose, owner, triggers, inputs, outputs, exit-code contract, and the invariants a check runs under. Consumed by `homelabnext.scripts` (`hnx scripts`, checklist M-01, M-02, M-04; docs/scripts.md) |

`service.json` (the service-registry row, 2.1 adds `status_sources`: what the status hub may poll or receive, by registry name, ADR-0013) is owned by the registry task and lives in this directory;
it is not part of this task's checks. Backends and services are always `svc:` ids, never URLs.
