- The Code Mode runner and the `codemode-runner` capability, the eighteenth (CM-5b of `docs/codemode.md`, ADR-0031 decisions 2, 3, 6, 7 and 10). `homelabnext.codemode.runner.Runner` is `codemode.execute`'s handler: it checks the execution request, asks the broker for the run's token as the bound runner (`issue_token`, the actor's granted actions, never `codemode.*`), serves the run's endpoint on the CM-4 wire and hands the program, the endpoint and the token to a `CodeExecutor`, and returns a `schemas/codemode/execution_result` held to its schema (status `ok`, `paused`, `denied`, `error` or `limit`; calls in step order with the broker's outcome, reason and request ids; `pending`; single-line `logs`; the value and `truncated`), spending the token `paused` or `finished`. Every program call is a broker request with the token, so `call` is `token_call`, `submit` is `token_submit`, the paused step on a resume `token_run`; over the socket the runner speaks as its `codemode.runners` peer and its relay as a `codemode.sandboxes` peer with the bearer line (`SocketRunnerBroker`, `SocketSandboxBroker`), and a call presenting another token is refused at the relay. An exec envelope is unwrapped to `output` (JSON when it is JSON, else text); a truncated output (`output-truncated`), a non-zero exit (`handler-failed`, the broker's), an output that does not match the action's result schema from the search index (`result-schema-mismatch`) and a result over the journal's cap (`result-too-large`) reach the program as `broker.Error`, while the record keeps the broker's outcome. A broker refusal is a denied call the program catches as `broker.Denied` with the broker's reason, with the request ids when the broker built the request and without them (never journalled) for a token refusal; a transport failure is `broker-unreachable`. The step journal (`homelabnext/codemode/journal.py`, `schemas/codemode/journal_step`) is local, append-only and durable: one directory per execution keyed per actor, one exclusively created `0600` file per record, a keyed fingerprint of each call (the request digest being the broker's), at most 200 steps, swept 7 days after an execution finished and 30 after it paused. A submit, or a call needing approval, pauses the run with `pending` naming it; a resume reads `token_status`'s `paused_by_state` (never polling `token_run`, which spends the cap) and, while the request waits, ends `paused` again unissued and having sent nothing; once it may run, journalled steps are answered from the journal (`replayed`) and never re-sent, the paused request runs by its id, only the later calls are new, and a call that differs from its journalled step is refused `replay-mismatch` and ends the run `error`. A call the broker refuses `call-cap-reached` ends the run `limit` (`calls`). The program's view gains `broker.submit(action, args)` and a `target=` keyword (the CM-4 wire's optional `op` and `target`; the forking test executor sends them). New tool class `codemode` (reader-forbidden, not broker-only: its tools only read, and running code is the broker action, already `exec`), `platform/mcp_server` 1.2 (additive: the class `codemode`; baseline frozen; example and negative); `cap:codemode-runner` classed `exec` and never a module's `shared_config` target; keyring rebuilt; client renders regenerated. Hardened after review: a request takes a step, and reaches the broker, only once the relay has accepted it (the run's token in constant time, an action and a `svc:` target matched whole, at most 200 steps), so a stray or co-tenant line cannot shift a resume's steps and re-send a settled call; the relay's own refusals are bounded (32, then the run ends `error`), it serves connections concurrently (8 at once, a 5 s read timeout or the run's wall budget), can check the peer's uid (`relay_uids`), and stops accepting before the result is built. The journal writes an intent before every call and its answer after, refusals without request ids included, so a resume answers every step the same way; a step of unknown outcome (an intent with no answer) is never sent again and ends the resume `error` (`step-outcome-unknown`), the paused step's being checked against `paused_by_state` instead; an answer that cannot be written stops the run, which ends `error` with its token spent `finished` and never resumes; an intent that cannot be written is never sent; a journal failure anywhere in `handle` is an `error` result; a crashed run is marked `interrupted` and never resumes; a resume is claimed by an atomic check-and-set (`Journal.update(expect=)`), so of two concurrent resumes one runs; records are validated against the schema and `meta.json` when read; directories are tightened to `0700`; results are bounded per execution (8 MiB) as well as per result. - Code Mode capability tokens, held and enforced by the broker (CM-5a of `docs/codemode.md`, ADR-0031 decisions 2, 6 and 7; `docs/broker.md` "Code Mode capability tokens"). `codemode.execute`'s params are checked as an execution request, and while its handler (the runner) runs the request is in flight, bound to its runner: only then, and only for that runner (manifest 1.7 `codemode.runners`, or in process `register_runner`), does `issue_token` mint one token for that run, its claims (`schemas/codemode/token`) taken from the request (id, authenticated actor, execution id, code digest), its actions each admitted for the actor by `decide()` (narrowing, never widening; never `codemode.*`), its lifetime within the manifest's `codemode` caps and the request's budget, at most a few live per actor. The call cap is per execution: a resume's token carries what is left of it. Execution ids are scoped per actor. The secret (256 random bits) is returned once; the broker keeps its sha256 with the claims, the runner, the state and the call count in `<state>/codemode/` (`homelabnext/broker/tokens.py`, a re-entrant lock over one `flock`). Every `token_call`/`token_submit`/`token_run` runs as the token's actor after, in order, `token-invalid` (one answer for an unknown and a wrong secret), `token-sandbox-mismatch` (both ways: a dedicated sandbox's token only from it, a pool only tokens bound to no dedicated sandbox), `token-expired`, `token-spent`, `token-paused`, `token-action-not-allowed` and `call-cap-reached` (`TOKEN_REFUSALS`); each call past those checks counts before `decide()`, so refused ones count too. Answers, and refusals raised once a request exists, name it (`request_id`, `request_digest`). A call that needs approval, and every submit, stores its request and pauses the token in one locked step (audit `token-pause`); `spend_token(..., outcome)` ends a token `finished` or `paused`, and the end of the execute spends a live one; only a paused execution resumes, and `token_run` runs the request it paused on once approved; `token_status` reports that request's state. A start-up sweep ends a run whose broker is gone as `crashed`, drops expired live entries and removes ended executions after `codemode.retention_days` (default 7). Socket peers `runner` (`token-issue`, `token-spend`, `token-status`; exempt from the refusal limit) and `sandbox` (`token-call`, `token-submit`, `token-run`, the token sent as a bearer line ahead of the JSON body and never in it; only pre-admission refusals count, keyed per presented token, with a ten-times-higher per-uid ceiling for unknown tokens whose audit records are coalesced); `BrokerClient` methods for each. With several manifest runners, `codemode.execute`'s action names its `runner`. A paused request an approver denied is refused `request-denied`, naming the request. The sandbox socket framing is specified (`docs/broker.md`, "Sandbox socket framing"), and a `token-issue` answer carries the secret beside the result, never in it. Sandbox transport refusals with no token read are coalesced per peer like unknown secrets, and a coalescing window that ends with refusals held back is flushed (a timer, the token sweep) with its count, judged on the monotonic clock. `token_run` counts against the cap past its binding check, refused or not, so polling is bounded; `paused_by_state` reports `expired` for an approval that expired unused (the request waits for a fresh one). New test hook `approval-control` (`decide_request`) and check `token-run-names-a-denied-request` with its mutant. Schemas: broker manifest 1.7 (`codemode`), audit 1.3 (`token-issue`, `token-pause`, `token-spend`, `token_id`, `execution_id`), both frozen; `schemas/codemode` drafts: the request-less reasons are `TOKEN_REFUSALS` plus `broker-unreachable` and `rate-limited`, and the cap is per execution. Contract: the broker's `CodemodeTokens` (feature `codemode-tokens`) with the reference fake, and its checks as the extended suite `broker-tokens` (the broker suite would pass the 24-check ceiling): thirteen MUST checks, each of its fourteen mutants caught by its own check alone (now asserted for `broker-tokens` and `codemode-executor` in `tests/conform/test_conform_mutants.py`); the reference service passes it (`conformance/targets/broker-reference.yml`).
- Context packs can carry levels (ADR-0032, `docs/agent.md` "Linked knowledge"): an `include:` rule takes an optional `detail: full | summary | outline` (`agent/profile` 1.4, additive; baseline frozen, with an example and a negative). `full` is the default and changes nothing: it is never written to the normalised rule, so existing profile digests and packs are byte-identical. `summary` puts a node's id, kind, title, path and level-0 summary in the pack instead of its body (a node with no summary is its title line and `(no summary)`, recorded as `summary_source: none`, never the full text); `outline` adds the heading outline with slugs, paths and sizes for the MCP `section` tool. The pack's knowledge record keeps the digest of the full content and adds `detail`, `summary_source` and `content_chars` to a non-full node; `max_chars` caps what is emitted. The generated capability and system pages (`hnx docs capabilities generate`, `hnx docs systems generate`) now carry a derived front-matter `summary:` (a machine-owned key, outside the review digest), marked `summary_generated: true` so the MCP tools, the pack and `hnx registers summaries` report it as `generated`, not `authored`. - `compose_app` refuses root however it is spelled: the explicit-root check compared the user part with `0` and `root` as text, so `user: "00"` or `"000:0"` (which the runtime reads as uid 0) passed; a user or group that is `root` or all zeros (`00`, `000:0`, `1000:0`, `root:root`) now needs `compose_app_allow_root`.
- `private_leak_check public` can no longer be switched off by the change it checks, and finds SOPS files by content: `lab/` and `ansible/inventory/production/` are pinned in the tool (the skeleton marker may add paths; one that drops a pinned path is a `private-paths` finding), where before deleting or editing `examples/private-overlay/.hnx-private-overlay.yml` in the same pull request emptied the list; and every file that reads as text is checked for SOPS ciphertext, not only `.yml`, `.json`, `.env` and `.ini` (sops writes any format under any name, e.g. `wg0.conf.enc`). `/examples/private-overlay/` has its own CODEOWNERS line.
- A plain deny-list term (the leak scanner's `--denylist`/`HNX_DENYLIST` and the context screener) matches its separator variants: `-`, `_` and `.` no longer count as part of a word, so `name` also matches `name-core`, `name_core`, `name.example` and `name2`, and the separators inside a term match any run of `-`, `_`, `.`, spaces or none (`some-name` matches `some_name`, `some name`, `somename`). A real host name built on a deny-listed word passed every pattern before.
- The `tailscale-acl` target keeps every value on one line: a `tailnet.deploy` exception reason (or any other `tailnet.deploy` value) holding a line break, NUL or Unicode line separator is refused by `deploy_problems` (so `hnx site validate` and `hnx guests render` both refuse it), and the renderer checks each `//` header line itself; a reason with a newline used to end its comment and write raw text into `tailscale-policy.hujson` ahead of the policy.
- `tools/fix_has_test.py --prove` (Q-08) no longer passes a fix it cannot prove: it counted pytest exit 2 on the parent (a collection or import error, e.g. a test module importing a name the fix adds, whatever it asserts) as "fails without the fix", and passed a fix whose only test files were fixtures, `conftest.py` or a non-test file under `tests/`. The parent run now uses `--continue-on-collection-errors` and a junit report and needs at least one failed test; the other cases are reported as "cannot prove" unless the commit carries a `No-regression-test:` trailer.
- The DCO job exempts Dependabot by the pull request GitHub records, not by the commit: the exemption keyed on an author email matching `<n>+<name>[bot]@users.noreply.github.com`, which any contributor can set with `GIT_AUTHOR_EMAIL`; now only commits authored as Dependabot in a pull request whose `user.login` is `dependabot[bot]` and `user.type` is `Bot` skip the sign-off.
- The tests that call external linters and validators now run in CI: a new `external-tools` job installs actionlint v1.7.11 and nats-server v2.10.22 (the lab image's version) by `go install`, each module sum pinned and compared before install, and zizmor 1.31.1 from a sha256-pinned wheel, lints this repository's workflows and actions (actionlint; zizmor at medium and above), and runs the private-overlay template and lab-in-a-box tests with `HNX_REQUIRE_TOOLS=actionlint,zizmor,nats-server,docker`, which turns a listed tool's "not installed" skip into a failure (`tests/suite_policy.py`). Before, the deploy templates were never checked by actionlint or zizmor anywhere. dnsmasq (an apt package, not pinnable by version) and playwright for node (a browser download) are still not installed.
- `tools/fix_has_test.py` is no longer counted as a test file: its name ends in `_test.py`, so a fix that touched only the gate passed the "ships a regression test" check, and `--prove` staged the fixed gate on the parent.
- `compose_app` no longer lets docker compose interpolation reach a mount: the template writes every `$` as `$$` in every rendered value (a volume `${X:-/}:/host` became the host root, `${X:-/var/run/docker}.sock` the docker socket, and `environment: {A: "${HOME}"}` the deploy host's value, because compose interpolates the rendered file from the environment of whoever runs `compose up`), the validator refuses a volume holding `$` or a source starting with `~`, and role lint RL014 flags such a bind source in a role's defaults, vars or templates.
- `compose_app` bind sources are an allow-list: a host path must lie under `compose_app_bind_roots` (the application's own directory and data directory by default; a host-wide root such as `/etc`, `/var` or `/srv` is refused) or be listed on its own with a reason in `compose_app_bind_extra`; relative sources and named volumes need neither. The deny-list it replaces let `/etc`, `/proc`, `/dev`, `/boot`, `/root`, `/run/systemd`, the D-Bus system bus, `buildkitd.sock` and `/var/lib/rancher` through. The runtime sockets still need `compose_app_allow_docker_socket`.
- `tools/fix_has_test.py --prove` applies one rule to Python and Go: a test that fails on the parent only because it does not build, collect or import counts as failing only if every such error names a symbol, module or Go package that the fix's own diff adds (read from the parent run's junit report, or from the Go compiler's `undefined:`/`has no field or method`/missing-package errors); any other build, collection or import error, and any error that is not a failing test, is "cannot prove". Before, a Go package that did not build on the parent counted as failing whatever the error, a Python collection error never did, and an import of any name inside a test function counted. A fix whose only test changes are fixtures outside a Go package is "cannot prove" in both languages without a `No-regression-test:` trailer.
- The `external-tools` job builds actionlint and nats-server with the workflow's one `GO_VERSION` (its own `TOOLS_GO_VERSION`, a floating end-of-life 1.24, is gone) and checks that each installed binary's build info (`go version -m`) names the pinned module, version and sum: `go install` of a package path builds whatever module provides it, so a nested module tagged later would have been built unchecked.
- One required-tools mechanism: tests ask for an external tool through `require_tool()` in `tests/suite_policy.py` (the `go_toolchain` fixture, the docker, nats-server, actionlint and zizmor checks), which returns its path, skips with "<tool> is not installed", or fails where `HNX_REQUIRE_TOOLS` (or the older `HNX_REQUIRE_GO=1`, kept) requires it. The lab bind guard's first pass runs on its own (`lab_bind_guard_pass1`), so its allow path is tested again without docker, and the guard exits 3 when the local compose has no `config --environment`.
- `tools/fix_has_test.py --prove` runs a Python fix's tests on the parent the way it runs Go's: the test functions and `Test*` methods the commit added or changed (decorators included), and every test that reaches a module-level name the commit changed (a parametrize decorator reading a case list that gained a case, a changed fixture or helper, through other module-level names too), the whole module only when a module-level change names nothing or reaches every test unnamed (`pytestmark`, an autouse fixture, a `pytest_*` hook); a case list that gained a case is no longer missed when the same commit also edits another test in the module (the gate ran only that test and reported a correct fix as passing without it); a neighbouring test that already fails on the parent no longer proves the fix, and the parent run stays short now that it no longer stops at the first failure.
- Deny-list terms no longer join words across whitespace (a hyphenated agent-card name matched the ordinary English phrase, in the leak scanner and in the context screener's redaction): `-`, `_` and `.` inside a term still match any run of those or none, and whitespace matches only where the term itself has it; a term ending in a digit (an address) is not extended by further digits.
