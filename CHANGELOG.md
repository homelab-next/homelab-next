## [Unreleased]

### Added

- Broker service, stage 1 (ADR-0017, `docs/broker.md`): `homelabnext.broker.service.BrokerService` implements the `broker` capability on the reference decision evaluator and passes its conformance suite. Durable, conflict-free state (one exclusively created file per request, claim, result, approval, consumed marker, audit record and outbox event; audit schema `broker/audit` 1.0), so an approval is consumed and a request runs exactly once across processes. Write lanes give agents limited writes to their own memory and findings directories and file proposals into the records inbox, with path containment, size caps, schema validation and a machine reason for every refusal. Exec handlers run digest-pinned files without a shell, with params as JSON on stdin, a scrubbed environment, a process-group timeout, capped output and secrets by name. Approval-gated actions emit `decision.requested`, are approved or denied with `hnx broker approve|deny`, and run once. `hnx broker validate|submit|status|run|cancel|approve|deny|pending|audit`; manifest schema 1.2, handler schema 1.1; a walkthrough in `examples/broker/`. Stage 2 (a transport and MCP tool server, SSO approvals, a hub approvals page) is planned.
- First products bound to baseline controls (ADR-0016 decision 7): `siem-agent` -> Wazuh agent (`wazuh_agent`), `remote-access` -> Tailscale (`tailscale_node`, tags from the guest's zone), `network-sensor` -> Suricata (`suricata_enroll`) and `vuln-scan` -> Greenbone (`greenbone_target`, internal assessment targets). Baseline set schema 1.1 adds `apply: guest|central` and `group`: a central control renders one play on the product's host with the list of guests that need it. New inventory groups `cap_sensor` and `cap_scanner`, a `tailscale-acl` render target that generates the tailnet policy from the zone model and the site's zone-to-zone flows, and an `hnx_secret` lookup so roles take secrets by name only. Known limits are documented per role; the per-guest roles support Debian-family systems.
- Guest baselines and defense layers (ADR-0016, `docs/compute-model.md`): a product-neutral baseline set (`_baselines.yml`, schema `platform/baseline_set` 1.0) defines defense controls in six layers (identity, host, network, detection, data, recovery) and named baselines that extend one another; guest schema 1.3 adds `baseline` (one or more names, per-guest `add`/`remove` with a reason, or a documented `exemption`). When a set exists, every vm, lxc and host must declare a baseline or an exemption. Each control's product is bound in one place, its `role`; until then it renders as an explicit unbound gap. The inventory gains `baseline_<name>` and `control_<id>` groups, a new `baseline-playbook` target applies each bound role, `hnx guests baselines` prints a guest-by-layer coverage matrix (`--check`, `--require-bound`), the status hub has a Baselines page, and checklist F-19 runs in the invariants register. Example baselines: base, server, exposed, sensitive, scratch.
- Strategy to task (ADR-0015, `docs/strategy.md`): a discipline-neutral strategy layer as linked Markdown records. A strategy (mission, intent, end state, priorities, assumptions, constraints) with its objective cascade SO → OO → TO → TT; MOPs and MOEs carrying the seven doctrine fields and bound to a source (invariant, status source, records lane, manual or none) and computed by `hnx strategy measure` into append-only readings with red/amber/green rollups; requirements in three types, CCIR, FFIR and PIR, each supporting strategy objectives, with FFIR → CCIR and PIR → CCIR/FFIR links and nothing else allowed; RFIs raised from gaps, triaged to collection or production, expiring at their LTIOV. The doctrine rules are a data-driven policy (`examples/strategy/doctrine.yml`). Status hub pages: Strategy, Requirements, Objectives and RFIs. The example is fictional; a real strategy stays in a private repository and loads through the same loader.
- Status hub, stage 2: product collectors (`homelabnext/status/products.py`, registry service schema 2.3 with per-source `auth` by secret name): `poll-prometheus` (instant queries with thresholds, and firing alerts by severity), `poll-uptime-kuma` (public status-page API), `poll-stackstorm` (failed and running executions), `poll-nifi` (controller status and bulletins), and built-in mappings for the LLM orchestrator's queue summary and Agentmetry's audit status. API shapes come from each product's source and recorded responses; the lab-in-a-box now runs Prometheus and a provisioned Uptime Kuma, polled through the real collectors in the smoke test (StackStorm and NiFi are too heavy for the 4 GB lab and are tested against recorded responses).
- Status hub, stage 1b: agent activity from any runtime, local or cloud (`homelabnext/status/agents/`, `docs/status.md` section 6). A summary tier (`status/agent_activity` 1.0: session, runtime, model, tool name, counts, outcome; also the bus event `homelabnext.agent.activity`) feeds the Agents, Activity (with CSV/JSONL export) and Agent analytics pages, and stuck or errored agents appear on the main page. A detail tier (`status/agent_activity_detail` 1.0: prompts, commands, tool input and output, approvals) is redacted by the screener before storage, size-capped and purged by retention, never put on the bus, and served only through the front door: trusted proxy, a shared-secret header the generated Caddy site adds, an Authentik identity and the viewer group, with every view in an access log. Collectors: a Claude Code hook (`hooks/claude_code_activity.py`), an authenticated push listener (`hnx status ingest`, one token per sender), an Agentmetry JSONL reader and a file spool.
- Conflict-free writes (ADR-0014, batch 13): machine state of lessons, runbooks and docs/systems pages (reviews, recurrences, verifications, lifecycle transitions) lives in append-only sidecar event files (`<record>.events/`, one exclusively created file per event, `register_event` schema 1.0); `reviews`, `recurrences`, `last_verified` and the current status are derived on load, so the human-written record file has a single kind of writer. `hnx registers events migrate|add`. Agents change a status by filing a `register-transition` intent in the records inbox; `hnx registers decide` applies it under a lock against the review policy (two conflicting intents: exactly one applies). `homelabnext.runs.run_dir` gives each run a private output directory and `tools/run_output_lint.py` fails scripts that write scratch files elsewhere. `write_record`/`write_event` validate before an atomic write.
- Status hub, stage 1 (ADR-0013, `docs/status.md`): a read-only primary console that does not depend on agents. Services declare `status_sources` in the registry (service schema 2.1: poll-http-json, poll-file, push-event; targets by registry name, interval, staleness, timeout, a declarative or built-in mapping), `hnx status sources` and `docs/status/sources.md` are the menu, collectors normalise everything to `status/observation` 1.0 records and `status.observed` events, each source runs with its own timeout (a hung source goes stale without stalling the rest), sources that stop reporting go stale, and transitions page once through the state-diffed notifier. `examples/status/views.yml` defines the shell (a main page and a left menu of built-in panels or optional external apps such as Agentmetry and Grafana); `hnx status render|serve` give a self-contained, script-free page and a loopback-only, read-only server that refuses foreign Host and Origin headers (DNS rebinding) and sends a strict CSP. Status sources are graph nodes. Checklist O-05, O-06 and O-07 are PUBLIC-NOW.
- `context`, the fifteenth capability (batch 9): scoped retrieval for agents (`conformance/protocols/context.py`: `index`, `query`, `get`, `delete`), with a mandatory `allowed` scope, 13 MUST checks (the scope is never exceeded, hidden documents look missing and are never related through, inactive records are excluded, deterministic and budgeted ranking, re-index and delete leave no stale copy, hostile query text is refused safely), six mutants each caught, a built-in fake and a reference implementation (`homelabnext/context`) that indexes the repository's knowledge graph. A product such as OpenViking joins as an adapter.
- Read-only MCP server (batch 10): `hnx mcp serve` (stdio only; extra `homelabnext[mcp]`) exposes `list_capabilities`, `get_contract`, `get_schema`, `find_services`, `related`, `context_for`, `lessons_due` and `invariants_status` as deterministic, size-capped JSON built from the same code as the docs. `context_for` requires an `allowed` scope, `--scope-from-profile` derives it from a verified profile's grants, and a call can only narrow it. Registered as `hnx-catalog` (class `read`); see `docs/mcp.md`.
- Linked knowledge in context packs (batch 8): agent specs take `include:` rules (`from: capabilities|services|mcp|task`, `kinds`, `depth`, `budget`, `require_reviews`; profile schema 1.2) that pull the content of related lessons, runbooks, checks, schemas and docs from the knowledge graph into the pack's volatile section. Only nodes wholly about things the profile is granted enter, seeds must be granted (`IncludeViolation`, re-checked at verify and pack time), inactive records never enter, and the pack records included ids with digests and every exclusion with its reason (`hnx agent pack --explain`). Knowledge never adds a grant.
- Knowledge as records and a graph (batch 7). Lessons and runbooks are one Markdown file per record (`examples/registers/lessons/LL-NNN.md`, `runbooks/RB-NNN.md`) with schema-checked front-matter, a generated Links block and the same fatal validation, read through `homelabnext.registers.load_register`; `hnx registers split|join` converted the old files losslessly, and ids (`LL-NEW`, check-lost, check-dupes) work across the directories. Lessons are `pitfall` (graduates into a mechanism: `retired_by` an invariant, test or gate) or `practice` (graduates into a procedure: `incorporated_into` a runbook step or SOP section); inactive records stay as files but drop out of every query, and `hnx registers review` lists what is due (review, retire, incorporate, supersede, update, keep). A shared review model (`homelabnext/reviews.py`, `examples/review-policy.yml`) gives lessons, runbooks and docs/systems pages a `reviews:` list with agent `check`, agent `audit` (a second, independent agent; first named `challenge`) and human `approve` tiers: no self-review, the audit reviewer differs from every checker, no agent in a human slot, and reviews go stale when the reviewed content's digest changes (`hnx reviews digest`). The knowledge graph (`homelabnext.graph`, `hnx graph build|check|related`, `docs/graph.md`) links services, capabilities, products, adapters, checks, schemas, lessons, runbooks, invariants, scripts, profiles, skills, MCP servers and docs by typed edges read only from source files; CI fails on a dangling edge or duplicate id, `related` ranks what a task should pull in, and `docs/graph/` is a local build (not committed).
- A "Scope of security testing" statement in the README and SECURITY.md: all security testing the project describes is internal and authorized, against the operator's own lab.

### Changed

- Names follow use: the second, independent agent review is an **audit** (an independent agent audit that looks for what is wrong, missing or unproven). The review role `challenge` is now `audit` everywhere: `homelabnext.reviews` (`ROLES`, "agent audit" messages), `examples/review-policy.yml` (reviewer `agent:example-auditor`), the graph's `reviewed` tier, a profile's `include.require_reviews`, docs and tests; the example review events are renamed `*-review-agent-example-auditor.yml`. Additive and compatible: `register_event` 1.2 and agent `profile` 1.3 add `audit` and keep `challenge`, which `homelabnext.reviews.normalize_role` reads as `audit` with a `DeprecatedReviewRole` warning (never a failure), and a test fails when `challenge` reappears in `examples/` or `docs/`. A new **Terms and scope** context (`homelabnext/agent/terms.md`, generated into `docs/terms.md` and checked by `hnx agent terms --check` in `make check`) defines auditing, audit review, auditing tool, internal assessment / validation / engagement and the authorized scope (the operator's own lab), and keeps threat vocabulary for external threats; every session pack (`start_session`) carries it as the reserved stable section `terms` (a manifest cannot define, replace or drop it; it is in the pack digest), and the MCP server has a read-only `terms()` tool. README and SECURITY scope sections, architecture row 10 and ADR-0011 now say auditing tools and internal assessment.
- Neutral wording for internal security testing: architecture row 10, checklist L-04 and ADR-0011 describe authorized internal testing (now internal assessment, see the audit entry above).
- Releases are published to GitHub only for now; the PyPI publish job in `release.yml` is skipped unless the repository variable `PUBLISH_TO_PYPI` is `true`.

### Removed

- OpenFGA (`authz`) from the lab-in-a-box: it backed no capability or conformance suite, and authorisation in this design is the identity provider plus the broker's allowlists and bound approvals.

### Security

- Conformance false passes closed: broker per-command allowlist, records completion only of approved notes, idp forgeries on JWT-shaped tokens (alg=none, empty or tampered signature) and expiry without clock control, lake-query injection payloads and verbatim round trip, secrets leak scan over the cause chain and traceback, events redelivery and object-store key traversal. A `Skip` counts only from the suite itself, a MUST needing an undeclared test hook is `untested` (a failure), `run` enforces `MIN_CHECKS`, unknown `--check` ids fail, one mutant per gap, and X-10 reads the report from `--out`. Suites load only from a verified checkout or an explicit `--root`.
- Generator injection: service schema 2.0 restricts every interpolated free-text field to one line (patterns reject a trailing newline), every renderer refuses control and format metacharacters (`homelabnext/generators/safe.py`), and the Authentik blueprint is emitted as data. fleet_units refuses control characters, hardens units by default and retires units to `/bin/false`; Terraform strings escape `${`/`%{`.
- Safer defaults: guest schema 1.2 `cloudinit.sudo` (no sudo rule by default; `NOPASSWD:ALL` is opt-in), Proxmox firewall files named by vmid with a datacenter-enable check and optional default-deny egress, libvirt refuses VLANs and NIC firewalls it cannot honour, `ansible.cfg` checks host keys, `compose_app` keeps secrets in 0600 env files with `no_log` and refuses privileged containers, docker.sock and all-interface ports unless explicitly allowed, the example unit runs sandboxed as a non-root user, and the lab-in-a-box refuses a non-loopback bind while credentials are the published placeholders.
- Broker approvals: `expires_at` and a default TTL are enforced, future-dated and replayed approvals are refused, approvers come from a manifest allowlist with issuer-qualified, normalised identities (broker manifest and decision 1.1).
- Swap records cross-check step state against the transition log, hash a state digest into each transition, and support an HMAC key and an external head anchor (swap record 1.1). Context packs fence volatile sections with a nonce; profile ceilings come from a separately owned policy and digests can be pinned in a lockfile; a service can only narrow its host's scope; the HTTP clients refuse credentials over plain http, cross-origin redirects and unbounded reads; repository tools and SQL table names are verified before use.
- Supply chain: the leak scanner scans tracked files, fails on files it cannot read, no longer lets `scrub-allow` waive secrets, detects public addresses, compressed IPv6 and keyed literals, and can scan history and commit identities; wheels and sdists contain only tracked files and no symlinks; gitleaks allowances are value-scoped; CI pins actions and hashed dependencies, drops persisted credentials, and adds DCO, dependency review, pip-audit, CodeQL, Scorecard, Dependabot and a release workflow with provenance, SBOM and trusted publishing; register ids may be committed as `XX-NEW` and are checked in CI.
