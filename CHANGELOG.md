## [Unreleased]

### Added
- Site schema 1.6 adds `router.wan6`, the router's own IPv6 on its WAN (docs/network-model.md, "The WAN's IPv6 (1.6)"): exactly one of `static: {address, gateway}` or `ra: true`. `hnx site validate` requires a static address canonical, with no zone id, a /64 of global unicast (never unique-local, documentation, link-local, special-purpose or IPv4-embedding), not an anycast address of the /64 and outside every zone's `subnet6` and `delegated_prefixes6` prefix, and a gateway that is link-local or another usable address in the WAN /64. `linux` renders it as a drop-in for the WAN's own networkd `.network` file (`<wan_network>.d/50-hnx-wan6.conf`; the new option `wan_network`, default `10-<wan_interface>.network`) or an ifupdown `inet6` stanza (`interfaces.d/hnx-wan6`): `IPv6AcceptRA=yes` (SLAAC only, no DHCPv6, `UseOnLinkPrefix=no`) or `inet6 auto` for `ra`, an address and a default route via the gateway for `static`. `default.accept_ra` and `default.accept_redirects` are 0, the WAN takes no redirect or route-information option, and its `accept_ra` is set after `all`'s (2 for `ra`, 0 for `static`); every zone takes no advertisement (networkd: `IPv6AcceptRA=no` on a zone without `subnet6` too). nftables takes a router advertisement on the WAN only (link-local source, hop limit 255), in the input chain and the reverse-path exemption, and the RFC 4890 ICMPv6 input whenever the router has any IPv6; the forward chain drops IPv6 to a zone's prefix leaving by the WAN, before `established,related`, and an output chain does for the router's own, so a prefix advertised on the WAN cannot pull a zone's traffic out; NAT is unchanged. Prefix delegation is not expressed (ifupdown has no clean form). Other adapters ignore `wan6`, and validation (or `render`/`plan --adapter`) warns that they do. A site without `wan6` renders byte for byte as before, with the same IR digest.
- The module selection names the lab's own lake namespaces (`lab_table_namespaces: [{namespace, why}]`, `why` required; docs/modules.md, "Site selection" and "Lake tables, from the catalog"). With the list, `hnx modules check --running` reports a gathered table in a namespace that no module id binds, that is not the core's and that is not listed (`tables X runs in namespace N, which is no module's, the core's or the lab's`); `[]` says the lab keeps none. Without the list such a table is still not judged, and the check now notes that the lab's namespaces are not declared. The loader refuses a listed namespace that is listed twice, the core's (`ocsf`) or any module id's (`-` read as `_`). `hnx site review-tier` rates a namespace added, or the list dropped, human-approve, and a namespace removed, a `why` reworded or the list declared where it was absent owner. The full example profile lists two namespaces; two new selection negatives cover a missing `why` and a namespace of the wrong shape.
- The module census gathers the lake tables (ADR-0027 follow-up 9; docs/modules.md, "Lake tables, from the catalog"). On the host that runs the lake catalog, `module_census_catalog_url` (plain http on a loopback IP literal), `module_census_catalog_warehouse` and, optionally, `module_census_catalog_api_root` and `module_census_catalog_token_file` (a plain name in `/etc/homelabnext`, only with the URL) make the role run `hnx modules catalog-tables` there: the Iceberg REST catalog's top-level namespaces and their tables, listed with GET requests only, no redirect followed and no proxy, each page read to at most 1 MiB, more than 4,096 namespaces or tables a failure, and two minutes for the whole listing. The token file is read on the catalog host in one step (no link, a regular file with one link, the reader's own, no group or other access, one line of token characters), the task becomes root only to read it, and the token is never printed: an error names the request and its HTTP status, never the catalog's words, and only names reach the runner. Names not of the inventory's shape are left out and counted, as are namespaces nested in a listed one (counted, never listed) and a namespace gone before its tables were listed. The loader judges only `ocsf.*` and module-id namespaces, and the selection's `lab_table_namespaces` the rest (below). `hnx modules gather` reads the names strictly and fills `tables` (the union over every catalog listed; `not_gathered` when none was). The loader now judges a table in the core's namespace that is not one of the core's OCSF tables, and notes when the core's tables were not read. `RestCatalog` takes an `opener`, lists namespaces (`list_namespaces`, under a `parent` when given), caps both listings with `limit`, refuses a listing entry of another shape as a `LakeError`, and gives each HTTP error a `bare` text without the server's words.

- The module census gathers the MCP servers the installed clients register (ADR-0027 follow-up 9; docs/modules.md, "MCP servers, from the installed clients"). A host's `module_census_mcp_configs` lists its installed client configurations (`{path, client}`: `claude-code`, `generic`, `hermes`: a fleet host's clients), trusted overlay input whose files must be named as their client's configuration (`.mcp.json`, `<name>.mcp.json`, `mcp.json`, Hermes `config.yaml`). The role reads each in one step (`library/mcp_client_configs.py`: no link at any step; every directory and the file root's or the connection user's; no directory its group or others may write except a root-owned sticky one; a regular file with one link, at most 1 MiB, no blocking) and parses it on the host, so a configuration's text, which can hold secrets, never leaves it: the answer carries per file whether it is present and the server names it registers, and both tasks run with `no_log`. JSON files refuse duplicate keys, `NaN` and `Infinity`; Hermes files are read with PyYAML's safe loader with aliases and duplicate keys refused, and fail the census on a host without PyYAML. `hnx modules gather` checks the names again and fills `mcp_servers` (an absent file registers nothing; a name that is not an inventory name, or a file that does not parse, fails the census). The loader matches a registered name back to its catalog record by the record's instance template (`homelabnext.modules.loader.instance_pattern`): a name bound to a module only against that module's records, an exact id first, then the template fixing the longest prefix, a name several records still match reported as ambiguous; a template that begins with a placeholder other than `{id}` is refused (`template_problem`). A name bound to no module must be one of the core's MCP records when the core's catalog was read (`CoreNames.mcp_instances`, `is_mcp`). The `llm-orchestrator` client's catalog is not read.
- The module census reports the sockets each host listens on, and the loader judges each selected module's service row by them (ADR-0027 follow-up 9; docs/modules.md, "Service rows, by what listens"). The `module_census` role's new `listening_sockets` module reads the kernel's socket tables (`/proc/net/tcp`, `tcp6`, `udp`, `udp6`, each to a fixed size; a role var, `module_census_socket_tables`, so group_vars cannot repoint it) and each answer carries `listening`: every listening TCP and bound, unconnected UDP port as `tcp/<port>` or `udp/<port>`, with `@lo` for one bound only to loopback (a line that does not parse is skipped; more than 16,384 distinct sockets fails the census). `hnx modules gather` parses them strictly (at most 16,384 per host) into the draft `platform/module_inventory`'s new optional `listening` (per host). Rows stay in `not_gathered`, since a socket names no row; with `listening`, `hnx modules check --running` reports a selected module's row as declared on its placed host (a provider's per instance, on that entry's own placement; the census host of that name, or whose first DNS label it is, compared case-insensitively) but not listened on from an address other hosts can reach (TCP; UDP for `udp`; either for `dns`; a loopback-only socket answers no other host), and notes a row whose host it cannot name. The comparison is derived and one way: a port another program holds (a client's UDP socket included) reads as the row answering, a row with no socket on the host (NAT into another network namespace with no proxy process) reads as not answering, and an undeclared row is never seen.
- The module census gathers the running notifier's recovery pairs (ADR-0027 follow-up 9; docs/modules.md, "Notify pairs"). A process that owns a notifier (`hnx broker serve`, `hnx status collect --notify-topic`) given `--notify-pairs-dir DIR` (`HNX_NOTIFY_PAIRS_DIR`) writes the pairs it holds to `DIR/broker/pairs.json` or `DIR/status/pairs.json` (`homelabnext.notify.record`, schema version 2): when built and after each registration, the whole set each time, with when it was written, the host's boot id and the writer's pid and start time, mode `0644` (it discloses which pairs and module ids run on the host to its local users). `DIR` and `DIR/<owner>` are opened once with no link at any step and must be owned by root or the writer and writable by no one else; the lock (on the owner's directory itself), the temp file and the replace are relative to that open directory, so a planted link, a FIFO or a path swapped after start cannot redirect or block a write. No role here deploys the broker or the status hub, so the operator makes the directories (owners and modes in the docs). The first write, at start, raises; a later one that fails is logged, the pair is still held, and the record is written again at the next registration or report. `Notifier.register_pair` takes an optional `module` (the module a pair was loaded from; never guessed) and refuses the same title for another module; nothing in the core passes `module` yet, so a module's running pair is reported as no module's until a module loader does. Role `module_census` reads each owner's record at the fixed `/var/lib/homelabnext/notify-pairs` (`module_census_pairs_dir`) in one step with its `notify_pairs_records` module (no link at any step, directories writable by their owner only, a regular file of at most 256 KiB, a FIFO never blocks), with the host's boot id, clock and the start time of each record's process. `hnx modules gather` parses each strictly and counts only a record that still says what runs: not one from before the host's last boot, a broker record only while its process runs, a status record (one pass per timer run) only for 900 s; each other is noted. With no counted record the pairs are left out and noted as not compared. The loader now also judges a running pair bound to no module: it must be one of the core's own (`homelabnext.notify.core_pairs`) with the same recovery, or it runs but is no module's or the core's; without the core's pairs it says the pair was not judged. A record is the owning service's word about its own pairs, believed as a host's `systemctl` output is. `homelabnext.schemas.module_manifest.TITLE_RE` is the notify title pattern compiled.
- The module census gathers the agents the running broker serves (docs/modules.md, "Agents, from the running broker"; docs/broker.md). The broker gains an **operator** role and its one operation, `agents` (`hnx broker agents --socket PATH`, `BrokerClient.agents`): broker manifest 1.8 adds `operators` (`[{uid | user}]`, empty by default; a peer is listed once across all five roles), and no peer is an operator unless listed there, root included (an unlisted uid 0 is `unknown-caller`, as before). The answer is the agent keys whose profile the manifest both maps a transport peer to and grants something, names only, audited as the new operation `agents` (audit 1.4; the record names no key), and so is each refusal; an agent, a relay, the runner and a sandbox are refused it (`not-the-operator`), an operator is refused every other operation, and `hnx broker agents` names the `operators` key when refused. Role `module_census` asks it on a host whose inventory sets `module_census_broker_socket` (a path under `/run/`; with `module_census_hnx_cli`, an absolute path, default `/opt/hnx/bin/hnx`), from that one task as root (`become`), which the broker host's manifest lists as an operator, and writes the answer's lines as the host answer's `agents`; `hnx modules gather` parses each line as one agent key (anything else fails the census), fills the inventory's `agents` with the union over the brokers asked, and leaves `agents` in `not_gathered` when no host's census asked one.
- `hnx site review-tier --base REV | --ci-base [--root DIR] [--site REL] [--selection REL] [--json]` (`homelabnext.network.review_tier`): the review tier of a change to what the lab claims, against a base read through git (one resolved commit, `--no-replace-objects`, capped regular blobs; the head read like every loader input). The default is human-approve: a change is owner only where the check knows it widens nothing. Judged by their own rules, a narrowing being owner: in the site, a delegated IPv6 prefix added or changed, a zone added, a zone's `subnet` or `subnet6` changed or added, its egress opened (`internet` anything but `deny`, `one_way` off, any other key), a firewall `allow` added or changed or a `deny` removed or changed, the service exceptions reordered (first match wins), any `tailnet` change; in the module selection, an address added to `scope.trusted` or `scope.target`, an address removed from `scope.exclude` or a part declared where it was absent, any grant added. Owner because they widen nothing: `site_version`, `site`, `edge`, `power`, a zone's `purpose`, `tags` and `dhcp.lease_hours`, a selection host's `capacity`. Every other changed key is human-approve with its path (a zone's `vlan_id`, `gateway`, `dns`, `dhcp.range`; the `router`, `switches`, `dns`, `dhcp_reservations`, `adapters`; the selection's `profile`, `hosts` addresses and `isolated`, `slots`, `features`, `core`, `providers` and placements). Every change to the registry (`lab/services.yml`), to `lab/guests/`, `lab/modules/` and `lab/modules.lock` is human-approve as a whole (`hnx modules review-tier` reads only the repository's module roots). A new, removed, unreadable or sealed file (a top-level `sops` key), a mapping key that is not text, and a shape it cannot compare are human-approve (fail closed). Like `hnx modules review-tier` it exits 1 only when a human-approve change has no valid `CODEOWNERS` owner as of the base: the approval itself is the pull request's Code Owners review, which binds only where the branch rules require it. The private-overlay template's `checks.yml` runs it on every pull request (job `site-review-tier`: the pinned `hnx`, a full-history checkout, no secret), its `CODEOWNERS` names `lab/modules.yml`, `lab/services.yml`, `lab/guests/`, `lab/modules/` and `lab/modules.lock` beside `lab/site.yml`, and every template job that checks out the pinned `hnx` into `hnx/` first fails when the overlay itself carries an `hnx/`. `homelabnext/network/review_tier.py` joins the module review tier's governance files; `swap_evidence.changed_paths` lists what a working tree changes under given paths.
- The network side renders a zone's `subnet6` (site 1.4). The IR carries it with the router's address, the prefix's `::1` (`Interface.subnet6`, `Interface.address6`, `Policy.zones6`, `router_address6`), and every adapter renders each policy rule's IPv6 form (`ipv6_form`) right after the rule. A rule between zones has one when every zone it names has a prefix. An allow naming a host has none (hosts are IPv4-only, so IPv6 to them stays closed), while a deny naming a host denies the same traffic to the host's whole zone, so a later, wider allow cannot pass in IPv6 what the deny refuses in IPv4. An internet rule has one only from a routed prefix. `linux` renders the router's IPv6 address and router advertisements (networkd's sender, or `etc/radvd.conf` for `flavor: ifupdown`), IPv6 forwarding with `accept_ra = 0`, an `ipv6_addr` set per zone, ICMPv6 and management SSH to the router, and a strict IPv6 reverse-path check (`fib saddr . iif oif missing drop`; IPv6 has no `rp_filter`, and without it a host could claim another zone's source). `unifi` renders the networks' static IPv6 settings and the policy in `LANv6_IN`/`WANv6_OUT` inside the same allow-established, drop-invalid and default-deny frame as IPv4, so IPv6 between zones is never left to the controller's default. `dnsmasq` and `zonefile` are unchanged (no DHCPv6, no AAAA). A site without prefixes renders byte for byte as before, and its IR digest is unchanged (the IPv6 fields are left out of an IPv4-only site's IR). The router's IPv6 input takes only the ICMPv6 RFC 4890 requires (echo rate-limited), and the reverse-path check's exemption is on-link control traffic only (neighbour discovery at hop limit 255 and MLD at hop limit 1, from `::` or a link-local source). The controller's IPv6 rules use the IPv4 index range (2000 to 2999) and `protocol_v6`; that range, the field and the controller's own `LANv6_LOCAL` and anti-spoofing defaults are checked on the server. A host deny before a zone allow makes IPv6 stricter than IPv4 (the deny closes the host's whole zone): `docs/network-model.md` says so. The WAN's own IPv6 is `router.wan6` (site 1.6). A guest's IPv6 extra address may no longer be its zone's `::1`, in compute validation and the `hnx_address` filter alike.
- A site may declare the global-unicast IPv6 prefixes it owns (`delegated_prefixes6`, `platform/site` 1.5, additive): a list of `{prefix, why}`, the reason required. In the lab-only judgement any destination network inside one is the lab's; a guest's `outbound_allow` names IPv6 only through a zone, so in practice a zone's global `subnet6` inside a declared prefix, which a model runtime (a VM, a container or a physical host) may then allow through `zone:`; outside every one it still reaches the internet. `hnx site validate` requires each prefix canonical, a /48 to a /64 (what an ISP delegates to one site; a /32 would claim an ISP's whole allocation), global unicast outside `2001::/23`, the retired 6bone `3ffe::/16`, the reserved `2000::/16` and documentation space, with no zone id and nothing IPv4-embedding, and no two overlapping (`delegated_prefixes6`, `delegated_prefix6_problem`); the compute path judges the list again, since it reads the site file unvalidated, and a declaration that does not read is a site problem that holds nothing as the lab's. The zone-prefix and delegated-prefix rules share one checker (`_prefix6_problem`). Rendering, a zone's own prefix rules and guests' IPv6 extra addresses are unchanged. `hnx guests` and the topology map pass the declaration through (`site_delegated6`, `load_fleet(delegated6=)`). The declaration is the site's word, not a proof, and its `why` is a note, not a control: the private overlay's `CODEOWNERS` template now names `lab/site.yml`, which gates the edit only where the overlay's branch rules require an approving Code Owners review; without that rule it is unreviewed site configuration (a human-approve check on changes to `delegated_prefixes6` is a follow-up). A zone's `subnet6` and the `hnx_address` filter's prefix rule now also refuse the retired 6bone `3ffe::/16` and the reserved `2000::/16`.
- The module loader at deploy time and the inventory gathered from the hosts (ADR-0027 follow-up 9; docs/modules.md, "The loader at deploy time"). `hnx modules check --deploy` is the deploy's check: it needs `--overlay`, refuses `--examples`, and a lab input the overlay lacks (the selection `lab/modules.yml`, the role table, the core registry) is a problem instead of a fallback to the repository's examples. The private overlay's deploy workflow always runs it before anything changes on a host (a problem stops the run), and its `checks.yml` runs it on every pull request with the pinned `hnx` and no secret. A lab with none of `lab/modules.yml`, `lab/modules/` and `lab/modules.lock` (a dangling link counts as present) is checked as an empty selection, never skipped: the inputs that only judge selected modules are notes, and every running unit of a module is one the site does not select; with modules selected and no review policy, the check notes that every fetched module is refused. After the deploy the workflow always takes a census of what runs: role `module_census` (`ansible/playbooks/module_census.yml`, read-only, per host one `systemctl list-unit-files --state=enabled 'hnx-*'` and one `systemctl list-units --state=active 'hnx-*'`, with `systemctl` pinned on the command line, the answers written on the controller; a host name that is not a plain name is refused), `hnx modules gather DIR --out FILE` (`homelabnext.modules.census`: every fleet unit some host reports enabled or active, each line parsed strictly; a host that did not answer, an entry that is no listed host's answer, a link or an oversized file fails the gather; the census is a union across hosts, so a unit is not checked against the host it runs on), and `hnx modules check --deploy --running FILE`, a verification that fails the run after the deploy has applied. The gatherer binds nothing: a unit is a module's by its name, as before. The draft `platform/module_inventory` 1.0 gains `not_gathered`, naming the kinds an inventory does not report (a gathered one: service rows, MCP servers, agents and tables), which the loader notes as not compared; a kind left out without it is still refused. The core's own fleet units now have a source: the loader reads them from what installs them (every unit file a core role's tasks install through a `dest:`, families with one unit per instance included, and the units the egress and mirror generators write, each generator's `UNIT`), never from a list; a running `hnx-*` unit that is neither a module's nor the core's is a problem ("runs but is no module's or the core's"), an empty selection included, and a module unit named like a core unit is refused. A test scans every role file and the package for a unit name the loader does not read. Without `ansible/roles` under `--root` the core's units are not read: a note, and under `--deploy` a `registry` problem. The census sees only `hnx-*` services and timers, and it runs with the overlay's own Ansible configuration and inventory, so it is an alarm against drift, not a gate against a hostile overlay (which has root through `site.yml`); the docs say both. The loader has not run at a real lab's deploy yet, so ADR-0027 stays proposed.
- The module loader compares recovery pairs and the core's own MCP ids, agent keys and tables (ADR-0027 follow-up 9). The draft `platform/module_inventory` 1.0 gains an optional `notify_pairs` (the running notifier's `{problem, recovery, module?}`; no `module` is the core's): with it, a running pair is declared by its module, which the site selects, with the same recovery title, every selected module's pair runs, and a title runs once; without it the report notes that pairs were not compared. Per site, a problem title is declared once across the selected modules and its recovery is another title (`pair_problems`). The uniqueness check against the core's names now also refuses a module MCP server id from the core MCP catalog beside the registry (`mcp/`), an agent key the generated keyring holds as an agent principal (`hnx modules check --keyring`, else `lab/keyring/keyring.json`, else the example's), a table among the core's OCSF tables, a module whose table namespace is the core's (`homelabnext.lake.tables.CORE_NAMESPACE`, `ocsf`), and a module notify pair whose problem or recovery title is one of the core's own. The core's pairs are now written once, in `homelabnext.notify.core_pairs` (`CORE_PAIRS`), which the broker, the status hub, the power monitor, the model-call budget and the serving-config check register from; a test fails on a registration that writes a title in place. `Notifier.register_pair` refuses to re-register a problem title with another recovery (it kept the last one). A recovery title names one thing: it is not another pair's problem or recovery title. A notify title, in the manifest and the inventory alike, refuses controls, no-break and other spaces, and zero-width and bidirectional marks. With `--overlay`, the MCP catalog (`lab/mcp/`) and the keyring (`lab/keyring/keyring.json`) are the overlay's: a missing one is a `registry` problem unless `--mcp-catalog` or `--keyring` names it, never the repository's example; without an overlay a missing source is a note, and with `--json` the notes also go to stderr. An MCP record's id is its `id`, else its file's stem, as the catalog's loader takes it; a record-like file that is not `<id>.yml`, an id that is not its file name and a catalog over 1,000 entries are `registry` problems; the OCSF tables are read through the loader's capped reader. The core's own units were not compared yet (see the deploy-time entry above). The example small-lab inventory lists its notify pairs.
- The network sensor's rows carry the zone's IPv6 prefix: a central control's `<role>_guests` row for a guest with extra addresses now carries its zone's `subnet6` (site 1.4) after `subnet` when the zone gives one, and `hnx_enroll_address_problems` holds an IPv6 extra address to it, as guest validation does, so `suricata_enroll` no longer refuses a global IPv6 extra address validation accepted. The filter checks `subnet6` by the site's own prefix rules (canonical, a /48 to a /64, unique-local or global unicast less 2001::/23, never IPv4 written inside IPv6), refuses an IPv6 extra at the subnet-router or an RFC 2526 anycast address of its /64, holds no IPv6 extra to an unusable `subnet6` (or any extra to an unusable `subnet`), and, without `subnet6`, keeps accepting only unique-local and documentation IPv6 addresses.
- A guest's extra addresses (`network.extra_addresses`, guest 1.6) now reach the network sensor and the topology map. A central control's `<role>_guests` row carries `extra_addresses: [...]` after `ip`, and the zone's IPv4 `subnet` after `zone`, when the guest names any (rows of guests that name none are unchanged). `suricata_enroll` puts every address of every enrolled guest in `HOME_NET` and in its zone's `HNX_ZONE_<ZONE>`, IPv6 included, so traffic from a second NIC or a container's bridge address is no longer `EXTERNAL_NET`. Because `HOME_NET` is what the sensor trusts as the lab's own, the role first holds every address to the guest model's rules with a new filter, `hnx_enroll_address_problems` (`ansible/plugins/filter/hnx_address.py`; `ansible.cfg` gains `filter_plugins`, as does the private overlay's), which parses each address and names every bad one: canonical, never loopback, link-local, multicast, reserved, a cloud metadata address or IPv4 written inside IPv6; `ip` IPv4 and inside the row's `subnet`; an extra address inside the row's zone `subnet` (never its network or broadcast address) or the shared range a tailnet uses, and, in a hand-written row with no `subnet`, private, shared or documentation space only; IPv6 extras unique-local or documentation; a `subnet` a canonical /8 to /30 holding the guest's `ip`, no wider than /24 where it reaches public space. The topology map resolves a host, firewall source or destination at any of a guest's addresses, in any spelling, to that guest (a single-address CIDR, /32 or /128), and its card and table list the extra addresses apart from the address; the dataflow page's host line under a guest shows all its addresses. Where two guests claim one address, which a valid site never has, the map now keeps the first guest (a primary address always before any extra), where it kept the last. The vuln-scan and backup-verify roles still enroll `ip` only.
- A zone's IPv6 prefix (`platform/site` 1.4, additive): `subnet6`, a /48 to a /64, optional. `hnx site validate` requires it canonical (lower case, compressed, no host bits) and refuses a link-local, multicast, loopback or unspecified prefix, one that writes IPv4 inside IPv6 (mapped, compatible, translated, NAT64, 6to4, Teredo), and two zones' prefixes that overlap. A guest's IPv6 `network.extra_addresses` is held against it: inside its own zone's `subnet6` and never inside another zone's, so a global IPv6 address (a SLAAC one included) can now be listed and is ownership-checked; an anycast address of its /64 (the subnet-router one, and the top 128 interface identifiers RFC 2526 reserves) is refused. A prefix must come from unique-local, global unicast (less the IETF protocol assignments `2001::/23`) or documentation space. Where the guest's zone has no `subnet6`, the 1.6 rule stands (a global IPv6 address is refused; a unique-local or documentation one is accepted with no ownership check), now also refused when another zone's prefix holds it; a `subnet6` that `open_site` reads without `hnx site validate` is held to the same rule, and when any zone's `subnet` or given `subnet6` does not read (an empty or non-text one included) or the guest's zone is not in the site model, every IPv6 extra address is refused. `ZoneInfo` gains `subnet6`. The example zone `compute` has `2001:db8:0:82::/64`, so `infer-core`'s IPv6 extra address is ownership-checked. Nothing else is configured from it: the adapters remain IPv4-only (`zone:` references in guest firewall rules and egress validation: see Fixed).
- A guest's other addresses (`platform/guest` 1.6, additive): `network.extra_addresses` lists what else a guest sends from besides `network.ip` (a second NIC, a macvlan or bridge address its containers use, a unique-local IPv6 address), each a bare address with a `why`, at most sixteen. The `runtime-labels` render labels every one of them like `network.ip`, so a model runtime sending from its second address is still labelled `model` and the three model-runtime detections still fire (new evasion fixtures: a runtime calling itself `none` from its extra IPv6 address, the same address written uncompressed and upper-case, and its extra IPv4 address seen as a dual-stack peer; a test records the limit that a peer seen through NAT64 is not found). Only a schema that was never frozen, or a new major, may be a draft: `x-draft` on a major with any frozen baseline is an error. Baselines are found by the `$id` name, not the file name, two files may not carry one `$id`, and a frozen name no live schema carries is an error. With `--base REF` (CI: the pull request's base) `schemas/_frozen/` is append-only: every file there at REF must still exist, byte-identical. So `x-draft` cannot lift the additivity gate off a released schema while its baselines are kept, and the append-only check is what keeps them; `--ci-base` picks the base in CI: an unreadable pull request base is an error, a push whose previous tip is zero or gone (a new branch, a force-push) is compared with `HEAD^`, and any other event or a shallow checkout with no base is an error; the step prints the base it used, and the register-ids and regression-tests steps follow the same rule. Without a base a deleted baseline is not detected; a symlink under `schemas/_frozen/` is always refused.

Render generates the launch with fixed flags (`npx --prefix=<absolute npm_prefix>`, `uvx --no-config`), so the client's working directory cannot replace the pin, and settings, env and parameter keys may not configure the launcher; a third party's hosted server is an https `remote` URL. Check refuses literal secrets, unpinned launches and unreviewed records, and no message prints a value. A hosted server is an https URL naming a public DNS host (never an IPv4 address in any notation) and is `cloud-allowed`; a local-only profile is granted an internet-reaching server only by a named `internet_mcp` exception in the ceiling policy; no record sets a variable that loads code or redirects trust in the launcher (OpenSSL and TLS, proxies, glibc, shell and interpreter options); render refuses an `npm_prefix` that is the root, a symlink or not empty, and a symlinked `checkout_root`.
