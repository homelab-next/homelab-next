## Purpose

Bring a new server under the private overlay and run its first deploy, dispatched by hand through the Actions Environment, without the workstation and without a secret in git (docs/private-overlay.md).

## Steps

1. Create the private repository from examples/private-overlay/, delete `fictional: true` from its marker and protect main with the checks job required.
   - verify: python3 hnx/tools/private_leak_check.py private . prints clean (private), and a pull request shows the checks job as required
2. Generate the operator's age identity and the ansible-vault password offline, store both in the password manager and on paper, and put the age public recipient in .sops.yaml.
   - verify: git ls-files lists no age identity or password file, and the private leak check reports no key-file finding
3. Initialise OpenBao in server mode with TLS, keep the unseal shares and the root token offline, write the lab's credentials under their secret names, then revoke the root token.
   - verify: bao status reports sealed false, and a read with the revoked root token is refused
4. Create the deploy AppRole (read-only on the paths the deploy needs, token_ttl of minutes, a bounded secret_id TTL and source CIDRs), write the role credentials and the vault password under their secret names, create the deploy age identity, and re-encrypt the sealed files for the new recipient.
   - verify: sops -d on each lab/sealed file succeeds with SOPS_AGE_KEY set to the deploy identity, the AppRole token cannot read outside its paths, and after a test lookup bao list auth/token/accessors (as an administrator) shows no live token of the hnx-deploy role
5. Give the deploy a path into the lab: the tag:ci-deploy stanza in the tailnet policy (SSH plus an exception for the OpenBao port) with a Tailscale federated identity trusting repo:<owner>/<repo>:environment:production, or an ephemeral just-in-time runner (a fresh VM per job from a provisioner outside it, via generate-jitconfig) with runner/job-started.sh installed root-owned as ACTIONS_RUNNER_HOOK_JOB_STARTED and HNX_DEPLOY_REPOSITORY set in the service environment.
   - verify: the tailnet policy lets tag:ci-deploy reach TCP 22 of the deploy zones and the OpenBao port and nothing else; or a test workflow on a branch that names runs-on [self-hosted, hnx-deploy] fails at Set up runner with "refusing this job", and the runner list is empty again after a deploy
6. Create the Environment production with deployment branch main only (add required reviewers only on a plan that has them; on Pro or Team the API call must omit reviewers), the secrets BAO_SECRET_ID, SOPS_AGE_KEY and DEPLOY_SSH_KEY (ANSIBLE_VAULT_PASSWORD only if the vault password is not in OpenBao), and the variables HNX_REF, SOPS_VERSION, SOPS_SHA256, HNX_DEPLOY_PATH, BAO_ADDR, BAO_ROLE_ID, BAO_CACERT_PEM, HNX_VAULT_PASSWORD_REF, TS_OAUTH_CLIENT_ID and TS_AUDIENCE; protect main with a required approving review and Require review from Code Owners (.github/CODEOWNERS).
   - verify: a workflow_dispatch from another branch is refused by the Environment, the deploy's first step accepts the pins, gh secret list --env production shows no TS_ or HNX_SECRET_ secret, and a pull request touching .github/ shows the code owner review as required
7. Record each host's public SSH key in ansible/known_hosts after checking its fingerprint out of band.
   - verify: ssh-keygen -F <host> -f ansible/known_hosts finds every inventory host
8. Merge to main (checks.yml runs; deploy.yml does not), then dispatch the deploy with gh workflow run deploy.yml --ref main and watch the run end to end.
   - verify: the merge started no deploy run (gh run list --workflow deploy.yml), the dispatched run is green, its log shows no secret value (search it for each secret's first characters), and on the Tailscale path the tag:ci-deploy node is gone from the tailnet after the job
