# Provider, feature and core modules: the module manifest

> **Draft for operator review** ([ADR-0027](adr/0027-feature-and-provider-modules.md), proposed).
> This page, the **draft** schema `platform/module` 1.0
> ([`schemas/platform/module.schema.json`](../schemas/platform/module.schema.json), `x-draft`: not
> frozen, it may change until a loader and the pilot exist), the draft `platform/lake_table` 1.0,
> the fictional examples in `examples/modules/` and their contract tests
> (`tests/schemas/test_module_1_0.py`) exist. **There is no loader yet**: nothing reads a manifest at
> deploy time. Everything this page says "the loader checks" is the specification for that step;
> the contract tests apply each such rule to the examples (`homelabnext/modules/rules.py`) and show
> it refusing a planted defect. The schema, its examples and its negatives are generated by
> `python -m homelabnext.schemas` (`make schemas` and CI's `schemas` job check they are current).
>
> Sections marked **specified, not implemented** describe a record, generator or check that does
> not exist in any form yet, not even as a contract-test rule; [the follow-up
> list](#specified-not-implemented-the-follow-ups) names each one.

## Why

A lab's products change often: a DNS server, a case manager, three project trackers, a classifier
swapped four times in ten days, models and agent runtimes, a lake query engine, an object store. The
operator's rule is that **a swap is a configuration change plus a conformance run plus a data
migration, never a code change in the core or in a feature.** Two things stand in the way today:

1. **Products live inside core code.** Adapters sit in core packages and are imported directly;
   CLIs construct a product by name; schema enums list products.
2. **The core keeps lists of features.** A recovery-pair table, a scheduler list, a preflight
   script, a topology generator's inline data, a lake maintenance list, runtime homes with one block
   per agent. A cutover that edits twenty of twenty-two places makes no noise about the two it
   missed; a real one left a legacy timer armed beside the new one for three days and left the
   agent's production lane writing where no consumer read.

A **module manifest** fixes both: every product sits in a **provider module**, every optional
mission is a **feature module**, the core's own consumers sit in **core modules**, and each declares
what it needs, what it offers and every entry it adds to a registry the core builds.

## Words

| Term | Meaning |
|---|---|
| **slot** | A capability (`cap:<name>`) with a descriptor in the **slot registry**: a contract (`conformance/protocols/<file>.py`) and suite, or none yet (provisional). Where a standard interface exists the contract *is* that interface. |
| **provider module** | Fills one or more slots with **one product**. The only place a product name may appear. |
| **feature module** | An optional, removable mission (the external data collector, a sandbox, publishing). Names slots, model roles, interfaces and host roles, never products. |
| **core module** | Always installed, never removed, id `core-*`: the staff agents and the core's own consumers (scorecards, retention, the approval gate's readers), so a swap's dependants re-check sees them. |
| **interface** | Something a module offers *other modules* (a sample handoff, a publishable output). Defined once, by its owner; providers reference it. |
| **interchange format** | The neutral format at a boundary (OCSF, Sigma, CloudEvents, the S3 API, STIX, SARIF, ...). |
| **bundle** | Feature modules a site installs together (the SOC bundle), each still removable. |
| **site selection** | The overlay's `lab/modules.yml`: providers per slot, placement, lane bindings, real values, the **grants** a module cannot give itself, and the site's network **scope**. |
| **scope** | The site's addresses, in the selection's `scope:` block only: what is trusted (the lab's WAN, its networks, the operator's tooling), what may be targeted, and what is excluded. Private; public examples use documentation ranges. |

"Pack" is not used: it already means a workflow pack and an agent context pack. The status hub's
`module` field on a status source (a tile grouping) becomes `group` in service 2.7 (below).

## Where modules live

```text
modules/<id>/module.yml           a module shipped with homelab-next (none yet: this is the target)
  python/hnx_modules/<id_>/       its code: hnx_modules is a PEP 420 namespace package, so overlay
                                  modules add code without touching the repository
  roles/<id_>[_<role>]/           its Ansible roles (role interface v1)
  registry/ mcp/ agents/ prompts/ units/ invariants/ detections/ interfaces/ lake/ docs/ conformance/
examples/modules/<id>/module.yml  the fictional examples (this draft), examples/modules/slots.yml
                                  (the slot registry draft) and examples/modules/sites/ (profiles);
                                  never available to a site: the rules' default in-tree root is
                                  modules/ alone, and only the contract tests add this one
<overlay>/lab/modules/<id>/       a lab's private modules
<overlay>/lab/modules.yml         the lab's site selection and grants
```

The id equals the directory name and is the graph node `module:<id>`. An overlay module whose id
equals a shipped one is an **error**, never a silent override. The loader puts only
`hnx_modules/<id_>` of each module on the import path; a module shipping `hnx_modules/<other>/` or
`homelabnext/` is refused.

## The manifest at a glance

```text
manifest_version: "1.0"           # the schema version (const)
id: external-collector            # == directory name; never a reserved id; core-* only for kind core
kind: feature                     # provider | feature | core
title: / description: / owner: / author: (required) / status (+ reason, replaced_by) / version:
origin: {kind: in-tree}           # or {kind: git, url, commit} | {kind: archive, url, sha256}
bundle: {id: soc, group: threat-intel}             # feature only
product: {name, display, aliases, version}         # provider only
licence: {kind, spdx|expires, tier, renewal}       # provider only
credentials: [{secret, identity, holder, purpose}] # provider only; holder: provider|consumers|granted
control_plane: [{kind, reader, description}]       # provider only
identifiers: [{kind, name, on_remove}]
requires:  {capabilities, model_roles, interfaces, hosts, scope}   # hard
prefers:   {capabilities, interfaces}                         # soft, each with a fallback
interfaces: [{id, version, kind, schema|schema_id, description}]  # interfaces this module OWNS
provides:  {slots: {<slot>: {...}}, interfaces: [{interface, version, via}]}
egress:    none | [{host, to: [svc:...|internet], purpose}]
contributes: {roles, services, status_sources, notify_pairs, scheduler_jobs, lake_tables,
              preflight, mcp_servers, agents, invariants, entry_points, detections,
              workflow_packs, docs, shared_config}
data:      [{id, kind, table|prefix, via, description, export, import, retention}]
config:    {<key>: {type, description, default, values, overlay}}
lifecycle: {install, upgrade, remove: {playbook, export_first, discard_reason, audit}}
```

Defaults, so the common case is short: `lifecycle.upgrade` is `install` (roles are idempotent),
a host role's `exposure` is `internal` and its `count` 1, an agent's `lanes.production` is `real`,
`product.display` is `name`, `egress` is `none` when absent, and `purpose` is optional on every
requirement, host and egress entry (a `prefers` entry keeps it: with its `fallback.behaviour` it is
what a removal reports).

One schema covers the three kinds; `kind` switches the conditional fields, and every object is
strict (`additionalProperties: false`). There is no `x-` extension point on purpose: an annotation a
loader ignores is how a declared piece goes unchecked. References are the repository's ids
(`cap:`, `svc:`, `mdl:`, `profile:`, `table:`, `det:`) and graph node ids (`role:`, `status:`).

Examples (all fictional): providers
[example-object-store](../examples/modules/example-object-store/module.yml) and
[other-object-store](../examples/modules/other-object-store/module.yml) (one slot, the swap),
[example-siem-suite](../examples/modules/example-siem-suite/module.yml) (four slots),
[example-static-host](../examples/modules/example-static-host/module.yml) (hosted, provisional),
[example-platform](../examples/modules/example-platform/module.yml) (the privileged core slots),
example-orchestrator, example-agent-runtime, example-inference (an exclusive GPU), example-lake,
example-log-pipeline, example-detonation; features
[external-collector](../examples/modules/external-collector/module.yml),
[example-sandbox](../examples/modules/example-sandbox/module.yml) and
[publishing](../examples/modules/publishing/module.yml); core
[core-staff](../examples/modules/core-staff/module.yml) and
[core-modules](../examples/modules/core-modules/module.yml); profiles in `examples/modules/sites/`.

## The three kinds

### Provider modules

`provides.slots` is a map keyed by slot name, so a slot cannot be claimed twice. Each entry:

| Field | Meaning |
|---|---|
| `adapter` | `package.module:factory`: the module's own code (`hnx_modules.<id_>.`) or a shared conformance adapter (`homelabnext.conform.adapters.`, the allowlist); never any other callable |
| `formats`, `features` | boundary formats and the contract features it claims |
| `conformance.target` | a target file in the module; its features equal the entry's |
| `provisional` + `reason` | instead of `conformance`, **only** when the slot registry says the slot has no contract; never for a privileged slot |
| `migration` | `{formats, export, import}`: present **exactly** when the slot is stateful, in the slot's export formats |
| `calibration` | per (decision spec x provider) thresholds and input limits |

Provider-only fields: `licence` (the probe warns at 30 days, pages the module `owner` through
`notify` at 7, and turns the criterion red on the day), `credentials` (below), `control_plane`
(vendor-held configuration read by the module's own code for the conformance run). A hosted or
config-only provider with no host needs no `lifecycle`; its service rows take `version` from
`product.version` (never repeated).

### Feature modules

Optional and removable; no `product`, `licence`, `credentials`, `control_plane` or `provides.slots`.
Its own secrets are `config` keys of type `secret` in its own namespace. It may belong to a bundle
(`bundle: {id: soc, group: ...}`, membership on the member). The SOC bundle's groups:
`detect-respond`, `threat-intel`, `purple-audit`, `exposure-management`. A feature's service row's
`capability` alias is its module id (module ids and slot names never overlap); its MCP records front
no slot.

### Core modules

`kind: core`, id `core-*`: required, never removable (no `lifecycle.remove`, no `replaced_by`, never
`status: retired`), no product, licence, credentials, control plane or bundle. A core module is
always `origin: in-tree` and lives in the public `modules/` tree (the loader checks the location),
so a third party's manifest cannot make itself core and be selected on every site. Its host roles
are placed like any module's (`core.<id>.placement` in the selection) and its footprints are
counted. It has the same `requires`, `prefers`,
interfaces and contributions as any module. The **staff agents** live in a core module
(`core-staff`), not in the agent-runtime provider, so swapping the runtime never takes them with it;
the overlay roster assigns their codes. The core's other consumers (lake retention reading cases,
the approval gate reading classifier fields, the notify digest reading the detection source) get
core modules as their packages migrate. `core-modules` (the loader's own manifest) owns the criteria
that guard rules no module may contribute about itself.

## The slot registry (a draft schema; capability descriptor 1.1 when accepted)

Every slot has a descriptor; `examples/modules/slots.yml` is the draft data for the slots the
examples use, and the contract-test rules read it. The fields and their rules are a draft schema
of their own, `platform/slot` 1.0 (`schemas/platform/slot.schema.json`, `x-draft`): every
`slots.yml` entry validates against it, each contract names a real protocol file, and the
privileged set is pinned to the six trust roots named below, each with a conformance suite.
`platform/capability` stays 1.0 until the ADR is accepted: 1.0 allows undeclared keys, so adding
these fields' rules to it would refuse a 1.0 descriptor that happened to carry one, which is not
an additive change. Capability descriptor 1.1 takes them then (a deliberate, documented break, or
2.0). A `stage` slot need not declare `formats` unless it is `pass_through`, which must pass
something (non-empty `in` and `out`). The fields:

| Field | Meaning | What it makes computable |
|---|---|---|
| `contract` | the protocol file, or null; `contracts` may be empty only then | provisional **by declaration**: an undeclared `cap:` is a typo, not a slot |
| `stage` | SOC pipeline stage 1-10, or null (replaces nothing: `layer` stays) | pass-through neighbours |
| `formats: {in, out}` | boundary formats | pass-through is legal only when the selected upstream's out meets the downstream's in |
| `stateful`, `export_formats` | whether providers carry a migration, and in which neutral formats | no fictional migrations for stateless slots (notify, static hosting, edge, inference) |
| `required_in_core` | a site must select a provider | a selection cannot silently omit dns or backup |
| `privileged` | secrets, idp, edge (the front door), broker, orchestration, records | never provisional; always a conformance run and the human review tier |
| `pass_through` | the stage may be skipped | |

`implementations` is **derived** from provider manifests, never listed. `depends_on` (slot to slot)
is subsumed by the providers' and core modules' `requires`.

## `requires:` and `prefers:`

| Key | Entry | Notes |
|---|---|---|
| `capabilities` | `{cap, version, features, formats, instance, provisional, purpose}` | `version` is required unless `provisional` (then forbidden); provisional is refused where the slot has a contract |
| `model_roles` | `{role: mdl:<role>, purpose}` | a role alias; the model is bound once, in the site's role table |
| `interfaces` | `{interface, version, cardinality: one\|all, purpose}` | never names the offering module |
| `hosts` | `{role, kind, count, exposure, footprint, roles, purpose}` | by role; `exposure: internal \| internet-facing \| isolated`; `internet-facing` only on a `kind: external` role or with `grants.internet_facing` |
| `scope` | `{part, purpose}` | a part of the selection's [network scope](#the-network-scope) (`trusted.wan`, `trusted.nets`, `trusted.tooling`, `target`, `exclude.unattended_mutation`, `exclude.offensive`); the module reads those addresses from the selection, never from its own config. `requires` only: a module that reads scope has no fallback for it |

A `prefers` entry names a `fallback`: `behaviour`, optionally a lighter slot `to`, and optionally
`data` overrides. **A dataset bound to a preferred slot moves with the fallback**: a dataset's `via`
names the requirement it lives in, and when the site resolves that slot to its fallback, the
dataset lives in the fallback slot with the override's retention and formats. In the single-box
profile the external data collector's `sessions` falls back from the lake to the hot index with
`retention: {days: 30}` and `jsonl` export: the manifest's retention, export path and topology are
right on exactly the profile the fallback exists for. The loader checks that `fallback.data` names
one of the module's datasets living in that preference, that it has a `to` (the schema), and that
its formats are a subset of the `to` slot's export formats; a service row's `upstreams` follow the
same fallback.

Semantic properties a dependant relies on are contract **features** (`alert-promotes-case`,
`subday-timestamps`), so a dependant can require them and a swap that loses one is blocked.

### Footprint and resources

Each host role carries a `footprint` (`cpu`, `memory_mb`, `disk_gb`, optional `gpu_memory_mb`, and
`resources: [{kind: gpu, exclusive: true}]`). A site sums every footprint placed on a host, times
the role's `count`, **core and provider modules included**, over all four dimensions against the
host's capacity less its headroom. Every resource claim names a kind the host has; an exclusive
claim takes one of the host's named resources (`gpu0`) to itself, so two exclusive users of one
card are refused, and so is a shared user of a card someone holds exclusively. Every selected
module needs a manifest; nothing is exempt.

**Footprints as limits: specified, not implemented.** The intent is that the generated units and
guests take footprints as `MemoryMax`, `CPUQuota` and disk quotas, so an understated footprint
starves its own module, not its neighbours. No generator does this yet; today a footprint is only
summed by the contract-test rules.

## Interfaces: one owner (`platform/interface` 1.0: specified, not implemented)

An interface is defined **once**, in the owning module's (or a core module's) `interfaces:`: `id`,
`version`, `kind` (`object-prefix | event | lake-table | service`), the item schema (`schema`, a
`.json` JSON Schema in the owner's directory with `$id .../modules/<owner>/<name>/<version>`, or a
shipped `schema_id`; event `$id`s with dots are accepted) and a description. A **provider** of the
interface references it in `provides.interfaces` with `via: {cap, instance, prefix|table|service}`;
the prefix is in the provider's own namespace and the instance is one it requires. Ownership is per
**id**, every version included: the loader refuses a second module defining any version of an id
another module defines, and a reference to a version the owner does not define. The inline
definition is what exists; a standalone `platform/interface` record is not written.

**Gate ownership: specified, not implemented.** A gate interface is meant to be owned by the
consumer, whose gate input the schema is (`publishable-output` belongs to publishing,
`sample-handoff` to the sandbox). The manifest has no field marking an interface as a gate, so
nothing yet refuses a gate interface defined by its producer. Unselected modules'
manifests are still read for definitions; only selected ones run. The interface kinds
`agent-handoff` and `records-prefix` wait for a real module.

| Format | Where it lives today | Used at |
|---|---|---|
| `ocsf` 1.3.0 | [`schemas/ocsf/`](../schemas/ocsf/README.md) (`x-lake`) | collect, move & shape, store; findings |
| `sigma` | [`detections/sigma/`](../detections/README.md), `det:` ids | detect |
| `cloudevents` 1.0 | [`schemas/events/envelope.schema.json`](../schemas/events/envelope.schema.json) | respond (the bus) |
| `action-request` | [`schemas/broker/`](../schemas/broker/README.md) | act on hosts |
| `s3`, `sql`, `openai-compatible` | the object-store, lake-query and inference contracts | store, inference |
| `markdown-records` | the records lifecycle | understand, findings |
| `stix` 2.1, `sarif` 2.1.0, `ics` (RFC 5545) | **not in the repository yet** | triage, understand, assess; project feeds |

Neutral **export** formats (datasets and stateful slots, several per dataset): `parquet`, `jsonl`,
`csv`, `json`, `markdown-tree`, `object-tree`, `zone-file`, `sigma`, `stix`, `sarif`, `ics`. The list
is a draft enum; each slot descriptor names the subset it exports in.

### The SOC bundle, by pipeline stage

| # | Stage | Slots | Contract today | Boundary format |
|---|---|---|---|---|
| 1 | collect | `siem-source`, sensors | no (provisional) | OCSF events |
| 2 | move & shape | `log-pipeline`; may be **pass-through** | no | OCSF in and out |
| 3 | store | `object-store`, `lake-catalog`, `lake-query`; optional `hot-index` | yes; `hot-index` no | S3, SQL |
| 4 | detect | `detections` | yes | Sigma |
| 5 | triage | `fast-classifier`, `ioc-enrichment`, intel lookup | `fast-classifier` yes | STIX indicators |
| 6 | respond | `orchestration`, `cases`, `events`, `broker`; `soar` | yes for the first four | CloudEvents |
| 7 | act on hosts | `remote-admin`, behind the broker's approval | no | action-request |
| 8 | assess | `exposure-management` | no | SARIF or OCSF findings |
| 9 | understand | `threat-intel`, CTI pipeline, deep research; `records` | `records` yes | STIX + Markdown records |
| 10 | share | `static-hosting`, reachable only with the `publish` grant | no | a rendered static site |

A resource-constrained site selects fewer providers, not different modules: one provider fills
several stages (the SIEM suite in single-box), a stage is `pass-through` where the slot registry
allows it and the neighbours' formats meet, a slot is `none` when no selected module requires it,
and `prefers.fallback.to` binds a module to the lighter slot.

## `contributes:` and who approves what

The core builds each registry from every selected module's entries; **the core keeps no list.**

| Key | Record type | Replaces |
|---|---|---|
| `roles` | an Ansible role (role interface v1) | hand-kept role lists |
| `services` | `platform/service` rows; host names a module host role | hand-kept rows; health, metrics, front-door routes, DNS, topology, dataflow derive from them |
| `status_sources` | `status:<id>` declared on the module's own rows; the list and the rows' sources are equal | collector lists |
| `notify_pairs` | inline `{problem, recovery}`: **the notifier's only source** (code stops registering pairs) | a title-keyed dictionary |
| `scheduler_jobs` | a `fleet_units` spec file, or `timer:<own role>/<name>` | per-feature scheduler blocks |
| `lake_tables` | a `platform/lake_table` record file (draft 1.0); the core's OCSF tables get the same records | the lake-maintenance list |
| `preflight` | `{role, hook: readiness\|health}` | a preflight monolith with product branches |
| `mcp_servers` | a `platform/mcp_server` record | per-runtime client configs |
| `agents` | one block per agent (below) | ~15 definition sites per agent |
| `invariants` | criteria, ids `<module>/<slug>` | criteria in one central register |
| `entry_points` | `{group, name, object}`; `group` is an existing group only (`homelabnext.invariants.checks`) | core dicts of adapters |
| `detections` | a Sigma rule with its `det:` id | rule numbers in charters |
| `workflow_packs` | a workflow pack | — |
| `docs` | a Markdown page | a hand-edited docs index |
| `shared_config` | `{target, file, reason}` typed keys the target's generator merges | quirks in shared config |

Derived rather than contributed: **backup membership** (from `data` and stateful slots), **network
flows and firewall edges** (from `requires`, service `upstreams` and `egress`), **install order**
(from `requires`). Alert rules and dashboards are a follow-up contribution key.

### Trust tiers: what selecting a module grants

Selecting a module runs its code in core processes and its playbooks as root on its hosts. Each
contribution class maps to the gate and approver that already exist; none adds authority by itself.

| Contribution class | What it can do | Gate | Approver |
|---|---|---|---|
| roles, playbooks, lifecycle | root on the module's placed hosts | role_lint; the review tier below | human (all modules) |
| adapters, control-plane readers, entry points | code in core CLIs and runners | own package or the shared-adapter allowlist; tree digest | human for providers of privileged slots; owner otherwise |
| fleet units | scheduled jobs | `fleet_units` rules (dynamic user, full hardening); M-02/M-04 through the loader; `run_as_root`/`hardening_opt_out` are refused outright today (`grants.units` is in the selection schema but no rule reads it: not implemented) | overlay owner |
| service rows | routes, DNS, firewall edges | `public_hostname` needs `auth` other than `none` **and** `grants.public_routes`, whatever the auth; an upstream is a slot the module requires or prefers (following its fallback) or an instance it requires, and never `secrets`; a grant for broker, idp or remote-admin upstreams is not implemented | overlay owner |
| agents | an agent's profile | the overlay's `CeilingPolicy` (CODEOWNERS); compiled **only** with a policy | policy owner |
| MCP records | tools for agents | the catalog review policy from the core/overlay, never a policy beside the module | catalog reviewers |
| handoffs | broker actions | actions are a subset of the operator's broker manifest; never added to it | broker manifest owner |
| shared_config | keys in a shared component | never secrets, broker, mcp-catalog, records, orchestration, codemode-executor, codemode-runner; edge or idp only with `grants.shared_config` | overlay owner |
| egress | traffic beyond required slots | `egress:` declared, from the module's own host roles, to services that exist; each internet or authority-service target, and `external` for a `kind: external` host role, is named in `grants.egress.<module>.<role>`; an internet-facing role inside the lab needs `grants.internet_facing`; static hosting needs `grants.publish` | overlay owner |
| secrets | credentials | own namespace; cross-module reads need `grants.secrets` | overlay owner |

**Never contributed**: ceilings, broker actions and approvers, review policy, grants, and runtime
**tooling settings, hooks and instruction files** (left out of the schema until the tooling catalog
ADR defines reviewed kinds for them). `contributes.ceilings` and `contributes.tooling` are schema
errors.

**Manifests join the review policy** (`review-policy.yml` kinds `module-provider`, `module-feature`,
`module-core`) with the human-approve tier for any change to `credentials`, `control_plane`, agent
`needs` (data grants), `egress`, or a privileged slot. **Specified, not implemented**: the review
policy has no module kinds yet. The gates this table marks as implemented exist only as
contract-test rules over the examples (`homelabnext/modules/rules.py`); no loader enforces any of
them at deploy time.

### Names are bound to the module

| Name | Form |
|---|---|
| roles, entry-point names | `<id_>` or `<id_>_...` (`-` as `_`) |
| units, service rows, status sources, MCP records, agent keys, det ids | `<id>` or `<id>-...` (a provider's service row is keyed by its slot and renamed to the instance at bind time) |
| profiles | `profile:<agent key>` |
| tables | `table:<id_>.<name>` |
| data and interface prefixes | `<id>/...` in the slot they live in |
| records writes (lanes, write scopes, records-prefix data) | `<root>/<id>/` or `<root>/<id>-shadow/` (`findings`, `state`, `proposals`, `memory`) |
| secrets | `secret:<id>/...` |
| criteria | `<id>/<slug>` (registers/invariant 1.1) |

Reserved ids: `core`, `homelabnext`, `hnx`, `hnx-modules`, `lab`, `site`, `overlay`, `none`,
`pass-through`, `module`, `modules`, `all`, `any`, `self`, `shared`; and no id ends in `-shadow`
(the suffix names a shadow lane). "Starts with the id" means the id followed by a separator
(`-`, or `_` in the underscore forms), and a name belongs to the **longest** module id it is named
under: module `external` cannot claim `external_collector_edge` from `external-collector`. Across
modules, roles, entry-point names, agent keys, profiles, status sources, tables, identifiers, data
prefixes, MCP record ids, det ids, unit names and feature service rows are unique (a provider's
row is keyed by its slot and renamed to its instance), data prefixes do not overlap, and records
write prefixes (lanes, write scopes, records-prefix data) do not overlap. **Uniqueness against the
core's existing names** (its tables, units, det ids, profiles, roster keys) is specified, not
implemented: the core has no inventory of them for a rule to read.

### Agents: one block

```yaml
agents:
  - key: external-collector-analyst              # starts with the module id
    profile: profile:external-collector-analyst  # owned; never another profile (ceilings key on it)
    charter: agents/external-collector-analyst.md
    spec: agents/external-collector-analyst.spec.yml   # the one source of model role and capabilities
    needs:                                       # scopes only; caps == the spec's capabilities
      - {cap: cap:lake-query, access: read, scope: ['table:external_collector.sessions']}
      - {cap: cap:records, access: write, scope: [findings/external-collector/]}
    tools: [lake-query.query, records.write_note, external-collector-probe.last_batch]
    prompts: {real: prompts/....real.yml, shadow: prompts/....shadow.yml}
    schedule: {on_calendar: '*-*-* 06:10:00 UTC'}       # or trigger: {event: ...} | {interface: ...}
    roster: {recall: true}                       # staff codes are the overlay roster's
    lanes:
      real:   {writes: [findings/external-collector/, state/external-collector/]}   # production: real (default)
      shadow: {writes: [findings/external-collector-shadow/], compare_to: real}
```

- `needs` never names an authority slot (broker, secrets, idp, edge, remote-admin, mcp-catalog).
  Scopes are full table ids or prefixes with alphanumeric segments; write scopes are in the module's
  own namespace. A reader of untrusted text holds no acting capability (the compiler's reader rule:
  the object store is file-write), so the collector's analyst sees sample sidecars through the
  module's own read-only probe.
- **Lanes are per agent**: the real lane writes only `<root>/<id>/` and the shadow lane only
  `<root>/<id>-shadow/`, so shadow output never lands where consumers read. The selection binds
  each lane to exactly one orchestration instance (`features.<module>.agents.<key>.lanes: {real:
  platform, shadow: orchestrator}`; a core module's agents under `core.<id>`, a provider's under
  `providers.<id>`), and a binding for an agent key the module does not contribute is refused. A
  cutover is "real on the old instance, shadow on the new, then flip": expressible, and never a dual
  run.
- Tools are slot-named (`<slot>.<tool>`), and the slot is one the agent `needs` or one of the
  module's own MCP record ids, so a product-named tool (`northwind-objects.query`) is refused; the
  selected provider's MCP record implements them (its `capabilities` is the hook).
- The spec carries **no ceiling**: a module agent compiles only with the overlay's `CeilingPolicy`
  (the contract tests compile every example spec against one, and show compiling without one fails).

## `data:` and lifecycle safety

Each owned dataset: `id`, `kind` (`lake-table` needs `table`; `object-prefix`, `records-prefix` and
`files` need `prefix`; `database` and `state` have neither), `via` (the requirement it lives in:
required for `lake-table`, `object-prefix` and `records-prefix`, and naming only a cap, and an
instance, the module requires or prefers; `files`, `database` and `state` live on the module's own
host), `export` and `import` (`{formats: [...], via: role}`), `retention`. Roots: a prefix is relative to the
slot instance it lives in; files and path defaults are relative to the module's data root on its host
(`/var/lib/hnx-modules/<id>/`); contributed files to the module directory.

- Removal exports first (`export_first`, default true); `false` needs a `discard_reason`. A removal
  deletes only the module's own namespaced data, never another module's (the namespaces cannot
  overlap).
- **Import validation: specified, not implemented.** Each slot's and role's `import_` is meant to
  validate the tree it reads (no traversal, no symlinks, sizes and counts within the export
  manifest). No protocol states it as a MUST and no test exercises it.
- "Start empty" after a swap is a recorded decision with a reason (swap record 1.2).

Slot-level export/import (rule 3): each stateful slot's protocol gains `export(dest) -> manifest`
and `import_(src)` in the slot's export formats with a MUST round-trip check; role interface 1.1
adds `tasks/import.yml`; X-07 becomes slot-keyed ("every selected provider of a stateful slot passes
that slot's round trip").

## `config:`, credentials and identifiers

- Types: `string`, `integer`, `boolean`, `duration_s`, `path`, `svc`, `secret`, `enum`. Defaults are
  fictional. A key named like a credential (`password`, `token`, `secret`, `key`, `credential`,
  `api_key`, `private_key`) **must** be `type: secret`, whose default is a `secret:<id>/...` name. A
  string default carries no `<scheme>:` reference in any case (`secret:`, `SECRET:`, `vault:`) and no
  address literal: a module that needs addresses requires a part of the site's
  [network scope](#the-network-scope) instead. A path default is relative, without `..`. An enum default is a string, one of its
  `values` (loader).
- `credentials[].holder`: `provider` (only the provider's roles read it), `consumers` (a template:
  the provider issues one credential **per consumer** at bind time, never shared, so a swap revokes
  exactly the outgoing provider's), `granted` (readable only by modules the overlay's
  `grants.secrets` names: the static-hosting deploy token, read only by the publish gate's identity).
- Client environment names are slot-named (`OBJECT_STORE_ENDPOINT`), mapped by the provider.
- `identifiers` (hostname, dns-name, vmid, ...) with `on_remove: release | keep | tombstone`; the
  loader refuses an identifier another selected module or the core holds, so a removal never
  releases a name someone else uses.

## Egress and publishing

`egress:` is `none` (the default) or, per host role of the module's own, the registry services and
`internet` it may reach beyond the slots it requires; a `svc:` target must be a registry service
the site has (a selected slot or instance, or a selected module's row). A grant names its
targets: `grants.egress.<module>.<role>: [internet, svc:broker, external]`. Every `internet` target
and every authority or privileged service (`svc:secrets`, `svc:broker`, `svc:idp`, the instances
that fill those slots) must be listed for that role, and so must `external` for a `kind: external`
host role, which runs outside the lab and so is egress by itself. Because the grant lists targets,
not roles, a manifest change that adds a target to a granted role is refused until the overlay
lists it too. A host role inside the lab may be `internet-facing` only with
`grants.internet_facing.<module>: [<role>]`. **Every grant** (egress, internet_facing,
public_routes, publish, secrets, units, shared_config) names a selected module, and only what
exists for it: an egress target its entry lists, `external` for an external role, an
internet-facing role inside the lab, a row with a `public_hostname` (checked when the rows are
read), static hosting the module reaches, one of its units (when the unit specs are read), a
`shared_config` target it declares, and a credential another selected module holds (a grant of
the module's own secret is redundant and refused). For secrets that is as far as the manifest
goes: who actually reads a granted credential (an adapter, a gate's identity) is not visible in
it, so an unused secrets grant is not detected. A grant waiting for a role, row or target to appear
would switch it on with a module upgrade or a placement line nobody reads as a grant, so it is
refused ("... remove the grant"). So **a grant lands in the same overlay change as the module
version (its pin in the lock, or the checkout for an in-tree module) that first uses it, and is
deleted with the version that stops using it**; unselecting a module means deleting its grants. A
`svc:` target is checked even before the rows are read: a selected slot, an instance, or a name
bound to a selected feature or core module (whose rows then decide). **The egress generator is specified, not implemented**: nothing renders the declared egress
into host and unit network policy (`IPAddressDeny`/allow lists, nftables) yet, so today egress is
declared and checked against grants, not enforced on the wire. **Publishing is the only egress
for published content** because the overlay says so, not because publishing says so: only a module
in `grants.publish` may require, prefer or fall back to `cap:static-hosting`, and the core criterion
`core-modules/egress-publish-grant` checks it (deferred until the loader exists; the contract tests
apply it). The static host's deploy credential is `holder: granted` to the publish gate only.

The gate **verifies** a producer's TLP, never trusts it: an item's sidecar TLP is a claim; red,
amber and unknown are excluded; the body is scanned for TLP markers and deny-listed names, which
override the claim; only inert media types are accepted (`text/markdown`, `application/json`,
`image/png`) and the gate renders HTML itself. A grant for **cloud-bound model roles** is specified,
not implemented: the role table does not yet say which roles leave the lab.

## Placement and isolation

`exposure: isolated` (the sandbox's detonation guest, the detonation engine) lands only on a host the
site marks `isolated: true`, and such a host carries only isolated roles: no route to the lab, no
egress. External roles land only on `kind: external` hosts and vice versa. The compute model of
external hosts (IaC, image bake, access, the one-way path) is deferred to the collector pilot.

## Supply chain

`origin` is `in-tree` (shipped here; reviewed by this repository's pull requests),
`{kind: git, url, commit}` (a full 40- or 64-hex commit; the URL has no `.` or `..` segment) or
`{kind: archive, url, sha256}`. `in-tree` is bound to where the manifest is: the loader refuses
`in-tree` outside the public `modules/` tree and a fetched origin inside it, so a copied
third-party module cannot call itself in-tree. **Reviews never live in a module** (a module author
could ship pre-stamped approvals); `author` is required.

**The lock, the tree digest and digest-keyed reviews: specified, not implemented.** For a fetched
module the overlay is meant to keep a lock (`lab/modules.lock`: id, origin, tree digest = sha256
over every file of the module directory, code and roles included) and the reviews keyed by that
digest, so that unpinned, changed or unreviewed means not loadable. No lock format, digest tool or
review check exists.

## Site selection (`platform/module_selection` 1.0, a draft schema)

[`schemas/platform/module_selection.schema.json`](../schemas/platform/module_selection.schema.json)
(`x-draft`) is the shape; the three example profiles are its examples, and a misspelt or unknown
grant kind is refused rather than read as "no grants". Every cross-reference in it (a provider
fills the slot, an agent key exists, a grant is allowed, a config value is the module's own) is a
loader rule. Its own schema, beside the site model (profiles validate without a network model, and the selection
changes far more often than the site). Shape, as in the three profiles:

```text
profile: full
hosts:      {<name>: {kind, isolated, capacity: {cpu, memory_mb, disk_gb, gpu_memory_mb}, resources: [{name: gpu0, kind: gpu}], headroom: {memory_mb}}}
slots:      {<slot>: [{provider, instance, placement: {<host role>: <host>}}] | none | pass-through}
features:   {<module>: {placement, config, agents: {<key>: {lanes: {real: <orchestration instance>, shadow: ...}}}}}
core:       {<module>: {placement, config, agents: {...}}}   # core modules are always selected
providers:  {<module>: {agents: {...}}}             # a provider's agents (placement and config are per instance)
grants:     {publish: [...], egress: {<module>: {<host role>: [internet|external|svc:...]}},
             internet_facing: {<module>: [<host role>]}, secrets: {<reader>: [secret:...]},
             public_routes: {<module>: [<row>]}, shared_config: {<module>: [cap:edge|cap:idp]},
             units: {<module>: [<unit>]}}
scope:      {trusted: {wan, nets, tooling}, target, exclude: {unattended_mutation, offensive}}
```

A provider's agents have one lane binding for the module, under `providers.<id>`: it covers every
instance the site selects of that provider (per-instance agent bindings would be a later, additive
field). A config value must be a key the module declares; a secret-typed value is a secret in the module's
own namespace or one granted to it in `grants.secrets`, the same rule as a manifest default.
`capacity` stands in for the host's `platform/guest` `resources`, which a real selection references
by guest id instead of re-declaring. A multi-slot provider is placed once per instance. At run time a
consumer resolves a slot with **`provider_for(slot, instance)`** from the selection (today
`homelabnext/broker/cli.py` reads a conformance target file instead). Model choice stays one line in
the role table.

### The network scope

The site's addresses live in one place: the selection's `scope:` block, in the **private** overlay
(`lab/modules.yml`; seal the file with SOPS if its WAN addresses would hurt in a leak, as
[private overlay](private-overlay.md) describes for `lab/site.yml`). The public repository carries
only the schema, the enforcement and fictional examples in the documentation ranges (RFC 5737's
`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, RFC 3849's `2001:db8::/32` and RFC 9637's <!-- no-raw-endpoint: allow documentation ranges -->
`3fff::/20`).

```yaml
scope:
  trusted:
    wan: [203.0.113.32/29]                  # the lab's own public addresses (no-raw-endpoint: allow a documentation range)
    nets: [192.0.2.0/24, "2001:db8:30::/48"]  # its internal networks (no-raw-endpoint: allow a documentation range)
    tooling: [192.0.2.240/28]               # where the operator's own tooling runs from (no-raw-endpoint: allow a documentation range)
  target: [198.51.100.0/24, 192.0.2.0/24]   # what assessment tooling may touch (no-raw-endpoint: allow a documentation range)
  exclude:
    unattended_mutation: [192.0.2.1/32]     # no unattended job changes these (no-raw-endpoint: allow a documentation range)
    offensive: [192.0.2.0/28]               # never the target of offensive tooling; [] = none (no-raw-endpoint: allow a documentation range)
```

- **Entries.** Each part is a list of IPv4 or IPv6 addresses or CIDR networks. Quote an IPv6
  entry: YAML 1.1 reads an unquoted all-digit value such as `1:20:30` as a number. The schema and
  the loader match one pattern (`ENTRY_PATTERN` in `homelabnext/modules/scope.py`, from which the
  schema's `scope` object is generated): no zone id, no whitespace, no leading zeros, no IPv4
  written inside or embedded in IPv6 (mapped, compatible, NAT64; an IPv4 target is never inside an
  IPv6 network, so such an exclusion would exclude nothing), no IPv4 host bits. The loader
  (`scope_problems`, `parse_entry`) adds what a pattern cannot say: IPv6 host bits, `/0`, any
  network touching the unspecified, loopback, link-local, multicast or reserved blocks, a network
  listed twice, and in `trusted.*` a network broader than **/8 (IPv4) or /32 (IPv6)**: trusting
  more is a blind spot, not the lab. `target` has no floor. `trusted.wan` also refuses private,
  shared (RFC 6598) and unique-local space: the internet never sees the lab as one of those, so it
  is a typo for `trusted.nets`. It reports a wrong-typed or unknown part itself, without relying on
  the schema.
- **Empty and absent.** A part is non-empty, except an exclusion: `exclude.*: []` means "nothing
  excluded". An absent part is never read as empty: a module that requires it is refused.
- **Declared reads.** A module declares the parts it reads (`requires.scope`), and
  `homelabnext.modules.scope.scope_networks(site, module, part)`, the reader a module is meant to
  call, raises `ScopeUndeclared` for any other part; an absent, empty (unless an exclusion) or
  malformed part raises `ScopeMissing`, never an empty list. The API is **cooperative**: nothing
  stops code from reading `site["scope"]` or the low-level `_part_networks` directly, or from
  passing a module dict with an edited `requires`. What enforces the declaration today is review
  of the module's code and the loader's rule that every declared part is present; there is no
  sandbox between a module and the selection. The external data collector requires `trusted.wan`,
  so sessions from the lab's own WAN are dropped instead of reported, without a list of its own.
  It does not read `trusted.tooling`: the operator's own scanners and runners seen from outside are
  recorded like any other source (a site that wants one dropped lists it under `trusted.wan`).
- **Modules that read addresses.** The manifest has no "offensive", "mutating" or "acts on"
  marker, so the loader keys the rule on what a manifest declares, and fails closed: a module that
  requires any address part (`target` or any `trusted.*` part) must also require
  `exclude.offensive`, and `exclude.unattended_mutation` too unless it is attended. A module is
  **unattended unless every contribution kind it uses is inert** (`INERT_CONTRIBUTIONS`: docs,
  detections, lake tables, status sources, notify pairs); a service, a workflow pack, an MCP
  server, an invariant, an entry point, a preflight hook, a role, shared config, a scheduler job
  and every agent (each has a calendar or a trigger) can run with no human present, and a test ties
  the classification to the `platform/module` schema so a new kind counts as executable. The
  external data collector only filters on `trusted.wan`, but the manifest cannot say so, so it
  declares both exclusions and a site may set them to `[]`. A module acts only on
  `effective_targets(site, module)`: `target` minus those exclusions, per IP version; when the
  exclusions leave nothing it raises `ScopeMissing` ("nothing left after the exclusions"), never
  an empty list, which a caller could read as "unrestricted".
- **Addresses live here.** A module config default refuses an address literal (the schema's
  pattern, a dotted quad or `::`). A selection's string-valued config value (every type but
  `integer`, `duration_s` and `boolean`) refuses a site address (`address_literals`): an IPv6, hex
  or zero-padded address; any IPv4 address with a port, a prefix length, in brackets or in a URL,
  including an `inet_aton` short form there (`http://10.1/` is the octets 10, 0, 0, 1 and <!-- no-raw-endpoint: allow inet_aton short forms -->
  `10.20.5:8080` is 10, 20, 0, 5); and a plain dotted quad or 8 to 10 digit integer only when it is private or shared
  space. Let through: a plain global dotted quad and a plain short form (they read the same as a
  version), and unspecified, loopback, link-local, multicast, reserved and documentation addresses
  (bind addresses such as `0.0.0.0` and `[::]:8080`, labels such as `cafe::beef`). **Not scanned:**
  `integer`, `duration_s` and `boolean` keys. Their value is a number by schema, and any integer of
  2^24 or more is also an IPv4 address, so scanning them would refuse ordinary sizes; a module
  that reads an address out of an integer key is a defect in that module. An **external
  endpoint** (a public resolver, an NTP server) is a hostname or a `svc:` reference, never a
  literal; it is not part of the scope.
- **The public gate.** `tools/private_leak_check.py public` places the rule by **location**, not
  by format:
  - A site scope block may sit only at `SCOPE_BLOCK_PATHS`: the example site profiles
    (`examples/modules/sites/*.yml`) and the generated selection examples and negatives
    (`schemas/platform/{examples,negative}/module_selection.*.yml`). There the file is parsed
    strictly, after a size and depth bound (larger or deeper is refused before any parser sees
    it), every entry must be a string naming a documentation network (`scope-address`), the shape
    is the selection's with `scope` at the top level only (`scope-shape`: an unknown part, a key
    twice, an anchor or alias), and a file the parse refuses fails (`scope-unparsed`).
  - Everywhere, in **every file** the scanner reads (any suffix; CRLF and CR line ends are
    normalised first), two rules run and either one fails the file (`scope-address`):
    - **the parse pass:** a file that parses as JSON, TOML or YAML (by content, whatever the
      suffix; YAML only within the size and depth bounds) has every scalar, keys included, judged
      under any key whose resolved value is `scope` in any case, at any depth. An alias-spelled key,
      `? scope` with a comment, a CRLF `[scope]` header and a flow dedented anywhere are ordinary
      mappings here;
    - **the raw rule:** the raw text under every `scope` key is tokenised. A key is `scope` in
      any case, quoted or not: `scope:`, `[scope]`, `[[scope]]`, a dotted `scope.x` key followed
      by its own `:` or `=` (an attribute access or a call such as `scope.get(` is none), an
      assignment to a Python subscript such as `site["scope"]["target"]` (never a `==`
      comparison), a comment before the colon, the Markdown spellings `` `scope`: ``, `**scope**:`, `_scope_:`
      and a table row whose first cell is `scope`, and `scope =` at a line's start (TOML, INI)
      or spaced inside a TOML inline table. A call's keyword argument (`fixture(scope="module")`)
      and an HTML or XML attribute (`<th scope="row">`) are never keys. Keys are found again after
      decoding `\x`, `\u`, `\U`, escaped line breaks and HTML character references. The rule also
      reads what does not parse: Markdown prose and fences of any indent, length or info string,
      and each cell and textual output of a Jupyter notebook, joined from its per-line strings
      (both rules run on it). What a key holds is over-read: the rest of its line, every line
      indented deeper than the key's column, a value on the first later line with content, a
      quoted scalar or flow collection opened there through its close, and for a TOML header
      everything to the next header. A key's column is its first non-blank character, so an
      indented `scope = x` holds only the lines deeper than itself. A quoted or flow value on the key's line with nothing deeper
      is exactly that value, so the rest of a minified line is another key's. A YAML alias is
      followed to its anchor's last real definition (more than 256 aliases is itself a finding),
      and a value tagged as YAML binary fails.
    - **cost:** flow closers, anchors, TOML headers and line ends are indexed in one pass and no
      line is re-read per key. `test_the_raw_rule_grows_linearly` times ten shapes (among them
      the ones earlier versions were quadratic on) at n, 4n and 16n in CPU time
      (`time.process_time`, best of five, so a busy runner's other processes do not count) and
      allows at most 8x per 4x step; a quadratic shape grows 16x.

    An address-like token is an IPv6 address, a dotted quad in any numeric spelling, an integer
    of 2^24 or more in any YAML, TOML or C spelling, and an `inet_aton` short form of two or three
    parts that cannot be a version or a decimal: a hex part or a part over 255 (`81.2.17806`,
    `0x51.0x2458e`, also `1.300` or `3.14159`), or one in an address context (a prefix length such
    as `10.20/16`, a port, after `//` or `@`). Every other short form (`1.0`, `24.04`, `0.05`,
    `1.0.3`, and a bare `10.20`) is ignored, and a reading inside 0/8 never counts. Loopback,
    unspecified and link-local addresses name no site and are let through in both families, and
    an IPv6 form inside `::/96` is judged by its embedded IPv4 address, so `::` (a Python
    `[::-1]` slice, a C++ `Foo::bar`) is in 0/8; an IPv4-compatible or mapped form of a real
    address is still refused. The price of the integer and dotted-quad rules: an epoch, a byte
    size or a `YYYYMMDD` integer of 2^24 or more, and a four-part version (`1.0.0.0`), under a
    scope key are refused too. A page may show a block's shape with documentation addresses, so a doc-only block
    outside the allowlist is not judged for shape. A case variant of an allowlisted path is
    refused (`scope-shape`).
  - **Threat model.** The gate defends against an **accidental** commit of a real address in any
    ordinary format (YAML, JSON, TOML, Markdown, CRLF line ends, escapes, integer, hex,
    zero-padded and short spellings), and fails closed on what it cannot read. A **deliberately
    obfuscating** author is out of scope for a text gate and is review's to catch. Known non-goals:
    a hostname that resolves to the address it spells (`81-2-69-142.sslip.io`, `*.nip.io`), <!-- no-raw-endpoint: allow a non-goal example -->
    percent-encoded or ideographic dots, named HTML entities, Markdown backslash escapes or
    emphasis inside a number, and numbers spelt in words. Carriers no loader in this project
    reads as a scope are non-goals too: environment variables (`SCOPE_TARGET=` in `.env` or a
    shell), a CSV or TSV column headed `scope`, INI sections such as `[scope:lab]`, XML
    `<scope>` and HCL `scope {` blocks, YAML behind `//` comments or `>` blockquotes, a Markdown
    heading or bullet `scope` with the address on a later bullet, a TOML multi-line string inside
    a Markdown fence, and a notebook output that prints a scope's value without its key.
  - Parse-only layouts and the bounds. A few layouts only the parse pass reads (a YAML key
    spelled by an alias); in a YAML file over 256 KiB, or one nested deeper than the bounds
    anywhere, the parse pass does not run, so the raw rule alone judges it.
  - Not covered either: an address that is not under a scope key (a sibling key, plain prose) is
    `tools/leak_scan.py`'s, which ignores zero-padded and integer spellings; an integer below
    2^24 (it names no host); a version-like short form outside private space; a file the scanner
    cannot read as text (binary, over 5 MB), which `leak_scan` itself fails on.
- This block is the site's **network** scope. It is not `homelabnext.scope` ([scope guard](scope.md)),
  which keeps writer tools off scratch targets by registry id.

**Specified, not implemented**:

- **Dynamic WAN sources.** `trusted.wan` may list `{source: <name>}` instead of a network: a WAN
  from DHCP or CGNAT, or a delegated IPv6 prefix that changes. The schema accepts it so freezing the
  shape later is additive; the loader refuses it ("dynamic WAN sources are specified, not
  implemented") until a reader resolves a source.
- **A module that reads `target`.** No example module does yet; the rule above and
  `effective_targets` are ready for the first one.
- **Acting on names.** A module that acts on hostnames or `svc:` references is outside the
  network scope: the scope holds networks only, and the manifest cannot say a module acts on a
  name (nor that it only filters on a part, an `acts_on` marker), so no rule here covers it.

## What the loader checks

Specified here, applied to the examples by `homelabnext/modules/rules.py`:

1. **Per manifest**: id equals the directory and is not reserved; `origin: in-tree` exactly when the
   module is in the public `modules/` tree, and a core module only there; `replaced_by` is another
   module; every name is bound to the id (table above); code is own or shared-adapter; secrets in
   the own namespace; timers name own roles; every referenced role is contributed; agent rules
   (owned profile, prompts per lane, the real lane writing `<root>/<id>/` and the shadow lane
   `<root>/<id>-shadow/`, needs equal the spec's capabilities, tools on a needed slot or an own MCP
   record, no spec ceiling, a trigger names a consumed interface); criteria ids and evidence; fleet
   units (`fleet_units.validate`, namespaced, no root or opt-out, no direct paging); service rows
   (host roles, own status sources, public routes need auth, upstreams the module uses and never
   `secrets`); egress from own host roles; datasets `via` a cap and instance the module uses;
   fallback data naming an own dataset of that preference, in the fallback slot's export formats;
   interface schemas with the owner's `$id`; slot registry agreement (declared slots, provisional
   only without a contract, never for a privileged slot, migration iff stateful); enum defaults
   within values.
2. **Across manifests**: one owner per interface id (every version), no reference without a
   definition; every bound name belongs to the longest module id it is named under; unique names
   (the list above); no data prefix or records write prefix overlap.
3. **Per site**: every selected module has a manifest (core included); each features, core and
   providers entry is a selected module of that kind and binds only agents it contributes; config
   values are declared keys, carry no site address, and a secret value is the module's own or
   granted; the scope block parses strictly, and every part a selected module requires is present
   and non-empty (an exclusion may be `[]`); required core slots
   selected; instances unique; every hard requirement and instance satisfied; fallbacks selected
   and datasets moved with their data override; service upstreams follow the fallback; pass-through
   only where allowed and formats meet; interfaces provided, on instances their providers require;
   grants for publish, egress (internet, authority services, external hosts), public routes and
   cross-module secrets; every agent lane bound to exactly one selected orchestration instance;
   placements complete for features and core modules alike, external and isolated roles on matching
   hosts; footprints times `count` over four dimensions, and every resource claim against the
   host's named resources with exclusivity.
4. **Two-way, against what runs** (needs the loader): every contributed file exists, is a regular
   file inside the module (realpath containment, no symlinks), validates against its record type;
   every running unit, row, MCP server, agent, table and recovery pair has a manifest entry, and every
   entry a running thing.

## How a swap works, end to end

Swapping the `samples` object store from `example-object-store` to `other-object-store` (same shared
adapter, same instance name, same slot-named identifiers: the record keys on modules, never on
adapters or routes):

1. **Plan.** One selection line changes. The loader lists the dependants of `object-store/samples`
   (the external data collector and the sandbox require it; publishing reads through its interface;
   the lake requires the slot) **and core modules**, and opens a swap record 1.2.
2. **Conformance**: incumbent first, then candidate; data plane and field meanings.
3. **Dependants re-checked** against the candidate's version, features and formats; a dependant that
   no longer holds blocks the cutover. Fields whose meaning changes are recorded.
4. **Migration**: export from the incumbent in the slot's format, import into the candidate, with a
   boundary check (min, max, count across the cut), then dual-write and parity.
5. **Cutover and rollback window**: flip the binding; the instance name stays.
6. **Decommission**: the outgoing provider's issued credentials revoked, identifiers kept, released
   or tombstoned, `hnx decommission` plus the `contributions` plane (which takes a **module**
   target, not only a guest) clean.
7. **Close** with an ADR reference.

### Swap record 1.2 (draft: `platform/module_swap` 1.0)

What 1.2 adds to the record is the draft schema `platform/module_swap` 1.0, with its rules in
`homelabnext/modules/swap.py`; `platform/swap_record` stays 1.1 (its steps, gates and hash-chained
log are unchanged) until the ADR is accepted and the two are folded together. The swap kit
(`hnx swap`) still drives 1.1 records: no live swap has run through 1.2.

* **`dependants.report`**: one entry per selected module that requires or prefers a moving slot
  instance (a requirement naming another instance is not one; one naming none is), core modules
  included: `{module, kind, relation, slot, instance, checks: {features, formats}, verdict,
  reasons}`. Each check is `holds`, `fails` or `not-asked` against what the **incoming** provider
  offers for the slot; a failed requirement `blocks`, a failed preference `falls-back`.
  `dependants.blocked` lists the blocking modules, and a non-empty list refuses the cutover. The
  report is recomputed from the manifests and the site and compared, never trusted as written.
* **`route.selection_diff`**: `[{slot, instance, from, to}]`, exactly one line per moving slot
  instance from the outgoing to the incoming module, for a swap with no network route.
  `apply_selection_diff` is its cutover, and refuses a line that does not read `from`, so a diff
  cannot be applied twice or to another selection.
* **`legs`**: `[{instance, order}]`, every instance of the swap once, orders 1..n.
* The site checked against is the selection the swap **starts** from: each moving instance is
  served by the outgoing module there. `migration.format` is one both providers migrate the slot
  in, and its import count equals the boundary count; `credentials_revoked` names only the
  outgoing provider's credentials, and decommission waits until none is outstanding.

`tests/schemas/test_module_swap.py` drives the swap above (the `samples` object store) through
these rules end to end: plan, re-check, migration, cutover onto `sites/full.yml`, decommission. The
contract version a dependant requires is the slot's, not the provider's, so it is not part of the
re-check.


| Change from 1.1 | Why |
|---|---|
| `from_module`, `to_module` and `slots: [{slot, instance}]` replace `capability`, `from_adapter`, `to_adapter` | a swap is keyed on modules, slot and instance; one record links several slots (cases plus ioc-enrichment) |
| gate `modules-differ` replaces `adapters-differ`; an unchanged route is allowed | the same shared adapter and the same address are normal (the DNS swap kept its IPs) |
| `route` is one of `{endpoint: {host, port}}` or `{selection_diff}` | the scheduler cutover, a model-role rebind, a hosted static site and an engine behind an unchanged gateway have no network route |
| new step `migrate` between `shadow-start` and `dual-write` with evidence `migration: {export_manifest_sha256, import_result, boundary: {min, max, count}}` | export/import is gated, not prose |
| `start_empty: {reason, decided_by}` instead of `migration` | starting empty is a recorded decision |
| `dependants: {report, blocked: [...]}` gating `cutover`, including core modules | rule 2's promise |
| `meaning_changes: [{field, before, after}]` | a feed move changed what a rule id meant |
| `credentials_revoked: [secret:...]` gating `decommission-check` | the old provider's issued credentials go |
| `legs: [{instance, order}]` | the DNS swap's two-leg cutover across instances |

Model-role rebinds go through the same record with `{slot: cap:inference, role}`, golden evaluations
as conformance and calibration refit as a gate. Downtime migrations and derived-data rebuilds remain
open (below).

## The product-name lint (rule 1): specification

Modelled on `tools/no_raw_endpoints.py`. Not implemented in this draft.

- **Vocabulary**: every provider's `product.name`, `display` (lower-cased, spaces as `-`/`_`) and
  `aliases`, from the tree and the overlay; `tools/product_names.yml` for products without a provider
  module yet; **model identifiers** from the role table; and product-named environment variable
  prefixes (`<PRODUCT>_*`).
- **Where allowed**: inside a provider module; site configuration (the overlay, the public example
  sites); ADRs, the changelog and prose.
- **What is linted**: code, config keys and values, schema `enum`/`default`/`const`, CLI defaults
  and choices, file and directory names, env names, in the core and in feature and core modules.
- **Skipped**: comments, docstrings and Markdown prose. **Matching**: case-insensitive, bounded,
  `-` and `_` alike. **Suppression**: a path glob with a reason, plus a baseline that only shrinks.
- The contract tests already apply it to the examples (feature and core modules, sites, the slot
  registry).

## Migration path (no code moves in this draft)

1. Product-shaped code in core packages (about 28 adapter-shaped files) moves to provider modules
   one slot at a time behind the existing contract: lake, projects, automation, detection backends,
   status collectors (renamed to slot kinds), the front-door, metrics, identity and gateway
   renderers, serving engines, compute and network targets, notify senders, the conformance
   adapters, the secrets lookup's backend. Standard-contract slots first.
2. Contracts that import from adapters (`inference.py`, `classifier.py`) are inverted first.
3. Hard-coded selections become `provider_for(slot, instance)`.
4. Central lists become contributions; new entry-point groups are added as each lands (generators,
   status collectors, compute targets, network adapters, detection backends, serving engines, MCP
   clients, conformance adapters, capabilities), never promised in the schema first.
5. Agents: each feature agent's definition sites collapse into its block; staff agents into
   `core-staff`; the runtime dependency moves behind `agent-runtime`.
6. Pilots: the external data collector, then a greenfield module, then the sandbox (the first real
   interface). The schema is frozen when the ADR is accepted after the pilot.

## Specified, not implemented: the follow-ups

Everything below is described on this page and exists in no form yet: no schema, generator or
check, not even a contract-test rule. Each is a follow-up before the ADR can be accepted, or is
listed as deferred.

1. **Capability descriptor 1.1**: the fields and rules exist as the draft `platform/slot` 1.0, and `slots.yml` is validated against it; folding them into the descriptor waits for acceptance.
2. **Swap record 1.2**: `legs`, `selection_diff` and `dependants.report` are defined in the draft
   `platform/module_swap` 1.0 and one swap is driven through its rules end to end in a test;
   folding it into the swap record and the swap kit (`hnx swap`) waits for acceptance.
3. **`platform/interface` 1.0** as a standalone record, and a `gate` marker so a gate interface
   defined by its producer is refused.
4. **Trust-tier grants not yet implemented**: `grants.units` (root and opt-out units are refused
   outright instead), grants for broker, idp and remote-admin upstreams, cloud-bound model roles,
   `grants.shared_config` (the rule refuses edge and idp config outright), and the review-policy
   kinds `module-provider`, `module-feature`, `module-core`.
5. **Supply chain**: the `lab/modules.lock` format, the tree digest, and reviews keyed by it.
6. **The egress generator**: rendering declared egress into host and unit network policy.
7. **Import validation**: the MUST that `import_` refuses traversal, symlinks and oversize trees, and
   a test per stateful slot.
8. **Footprint limits**: generating `MemoryMax`, `CPUQuota` and disk quotas from footprints.
9. **The loader itself**: everything under "What the loader checks" runs today only over the
   fictional examples in the contract tests, plus the two-way check against what runs, uniqueness
   against the core's own names, and refusing an overlay module that shadows a shipped id.
10. **The product-name lint** (specified above).
