## What it does

Contract for `lake-query` and `lake-catalog`: the `LakeClient` of `homelabnext.lake`.

Subject = any object implementing `homelabnext.lake.LakeClient`:

    query(sql, params) -> list[dict]        portable SQL subset, `:name` parameters only
    named(name, params) -> list[dict]       registered queries
    describe(table) -> TableInfo            columns, key, row count, last committed mark per source
    list_tables() -> list[str]
    write_batch(table, rows, *, idempotency_key, source=None, high_water=None) -> WriteResult

Seeding goes through `write_batch`, so a read-only deployment either points the adapter at a
scratch namespace or declares a seeded copy.  Adapters raise `homelabnext.lake.LakeError`
subclasses (`RowRejected`, `UnknownTable`, ...); a suite accepts any `Exception` for
"rejected" but pins the observable effect (nothing written).

Commit `rows` atomically, at most once per `idempotency_key`.

A key that was already committed returns `replayed=True` and writes nothing. Rows whose
content key (the table's `key` columns) is already present are skipped, so a replay under
a different batching is also safe. `source`/`high_water` are stored with the commit
itself and come back in `describe(table).committed`.

`make_lake` builds a `homelabnext.lake.trino_rest.TrinoRestLake`: queries through the
`lake-query` endpoint (Trino), metadata and the batch ledger through the `lake-catalog`
endpoint (an Iceberg REST catalog such as Lakekeeper).  Both suites, `lake-query` and
`lake-catalog`, need the whole `LakeClient` (they seed through `write_batch` and count
through `query`), so both targets use this one factory.

Every subject of one run shares a scratch namespace `hnx_conform_<run>` (created with the pinned
tables on first use), so a run never sees another run's rows.  Plain `http` is accepted only to
a loopback address unless `allow_plaintext=True` (the same rule as `TrinoLake`).
