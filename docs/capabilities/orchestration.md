## What it does

Contract for `orchestration`: named jobs, idempotent submission, bounded retries.

`define` registers a job (a real adapter maps it onto a workflow/pack; the in-process form
takes a callable).  `submit` is idempotent per `idempotency_key`: a repeat returns the same
run and the job body executes once.  `wait` drives/awaits a run to a terminal state and returns
the run as it stands when `timeout` runs out.

**Holds.**  An orchestrator that admits work holds capacity for it: a slot, an exclusive lease,
a token or KV-cache reservation on a model backend.  The contract on every such hold (added
additively, ADR-0001; the reasoning is ADR-0029):

a. *Capacity is held only by live work, and live work keeps it.*  A hold exists only while the
   worker it was granted to is alive, and that worker keeps it until it ends: a hold that goes
   away on its own while its run is still executing is a timer, not a release.  A run in a
   terminal state holds nothing.  Holds are released on success, failure,
   cancel, deadline expiry, worker death and orchestrator restart -- never only by a TTL.  A TTL
   is a backstop for a defect in this contract, not the way holds end: a hold that outlives its
   worker until a timer fires is capacity taken from live work by dead work.  A run between
   attempts (an attempt failed and a retry is pending, backing off or waiting for a backend) is
   live: it stays `running` and keeps its holds.  Liveness is the orchestrator's own record
   of the run's worker, never whether an attempt's process happens to exist at that moment.
b. *Cancelling a running run stops it.*  `cancel` on a `running` run stops its worker; the
   run ends `cancelled` within `cancel_grace_s` (the subject's attribute, else
   `CANCEL_GRACE_S`) and its holds are released, whether or not the job body cooperates.
   A result the stopped worker produces afterwards is discarded.
c. *A restart reconciles.*  After the orchestrator restarts, no run is `running` without a live
   worker, and holds are rebuilt from live workers only.  A run that was executing is ended
   (`failed`), never run a second time: its old worker may still be executing elsewhere, and
   nothing it produces is recorded.  A run admitted but not yet executing may be requeued.  Queued runs survive and still run; idempotency keys survive, so a repeat
   submit after the restart returns the same run.
d. *Capacity is observable* (product feature `admission`): `capacity()` returns a
   `Capacity` -- the limit (`None` when the implementation does not report one), the
   number of holds in flight, and the run ids holding them.
e. *Faults can be injected* (test hook `fault-injection`): `kill(run_id)` makes the worker of a
   running run die as a crashed process would (the run must end `failed` and release its
   holds); `restart()` restarts the orchestrator in place, keeping its durable state and losing
   everything else, workers included.

A per-run deadline is the product feature `deadline`: `submit(..., deadline_s=s)`; a run
still unfinished `s` seconds after it was submitted ends `failed`, with an error that names
the deadline, and releases its holds.

  controller's profiles directory (`profiles_dir`, or `HNX_ORCHESTRATION_PROFILES_DIR`), then
  `POST /admin/reload-profiles`.  The agent key is `hnxconf-<run token>-<name>`; the profile
  is `local_only` and asks for `max_attempts: n + 1`, a field only a controller with the
  proposed retry change reads.  The handler is kept by the handler host, never sent anywhere.
* `submit` -> `POST /jobs` with that agent key, the idempotency key namespaced by the run
  token (the controller's keys are global and never expire), and a task description holding one
  job line (`hnx-conform-job:<base64url JSON>`: handler host URL, a token per submit and its
  HMAC, the job and its parameters).  `404` is `UnknownJob`.  The HMAC key never leaves
  the adapter process: the controller's `GET /jobs/{id}` (unauthenticated) shows the task
  description to anyone, so the line carries no host-wide secret, and the handler host runs only
  a token it issued, with a valid MAC, for that token's own job and parameters.  Its request
  body is bounded (`Content-Length`: not a number or negative is 400, over
  `MAX_RUN_BODY` is 413).
* the job body -> the controller runs `hermes -z PROMPT`; for a conformance run `hermes` is
  `conformance/fakes/llm_orchestrator_hermes.py`, which posts the job line to the handler host
  and prints the handler's answer (or exits 1 with its error).
* `wait` -> polls `GET /jobs/{id}` until a terminal state: `done` is `succeeded`,
  `failed` and `budget_killed` are `failed`, `cancelled` is `cancelled`; `result` is
  the answer decoded from `response_body`, `error` is `local_failed_reason`.  A controller
  that does not report `attempts` gets the number of executions the handler host saw for the
  run.  The timeout is at least `wait_floor` seconds: the controller admits on a 2 s tick.
* `cancel` -> `POST /jobs/{id}/cancel`; `409` (a run that may no longer be cancelled) reads
  the run back unchanged, which is the contract for a finished run.
* `capacity` (feature `admission`) -> `GET /admin/backend-inflight` (the route landed after
  `a52a1c4`; `hermesagent.Policy.InFlightSnapshot`): `in_flight` summed over the backends,
  `holders` the union of their `reserved_runs`, `limit` `None` (the snapshot reports no
  limit).  `admission` is declared only when that route answers; a `404` means no route, so
  the capacity checks skip, and any other answer (a 5xx, a timeout, a `401`) makes the run
  unmeasured rather than skipped.  Without a limit the suite judges a release by the run leaving
  `reserved_runs`: `in_flight` is a counter shared with any other traffic on the controller,
  so it is never compared.  With API authentication on, the route needs an admin token, which
  this adapter does not send.  The recorded stand-in is started only by the first contract call,
  and its features come from `fixes`, so a check that skips never starts one.
* `kill` / `restart` (test hook `fault-injection`) exist only on the recorded stand-in, which
  models the controller's process kill and restart reconciliation.  On a live controller the
  adapter has no honest way to kill one job's worker or restart the service, so it does not
  declare the hook: there the checks needing it are `untested` (a MUST cannot be skipped by
  leaving a hook out), unless the controller lacks `admission` too, in which case they skip.

The adapter never answers for the controller: it does not raise `UnknownJob` for a name it was
not given and does not retry a failed run itself, so the suite sees what the controller does.

Controller limits (of `a52a1c4`, not of this adapter): an unknown `agent_key` is accepted and
queued as an HTTP passthrough job (`unknown-job-raises` fails); a run is attempted once
(`retries-until-success` and `retries-are-bounded` fail); a submit cannot be held, so a cancel
races the next admission tick; the API has no authentication.
