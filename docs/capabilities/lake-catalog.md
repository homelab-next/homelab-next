## What it does

Contract for `lake-query` and `lake-catalog`: the `LakeClient` of `homelabnext.lake`.

Subject = any object implementing `homelabnext.lake.LakeClient`:

    query(sql, params) -> list[dict]        portable SQL subset, `:name` parameters only
    named(name, params) -> list[dict]       registered queries
    describe(table) -> TableInfo            columns, key, row count, last committed mark per source
    list_tables() -> list[str]
    write_batch(table, rows, *, idempotency_key, source=None, high_water=None,
                expect_source=None) -> WriteResult

Seeding goes through `write_batch`, so a read-only deployment either points the adapter at a
scratch namespace or declares a seeded copy.  Adapters raise `homelabnext.lake.LakeError`
subclasses (`RowRejected`, `UnknownTable`, ...); a suite accepts any `Exception` for
"rejected" but pins the observable effect (nothing written).

**Returns:** `WriteResult`

Commit `rows` atomically, at most once per `idempotency_key`.

A key that was already committed returns `replayed=True` and writes nothing. Rows whose
content key (the table's `key` columns) is already present are skipped, so a replay under
a different batching is also safe. `source`/`high_water` are stored with the commit
itself and come back in `describe(table).committed`.

A replay is judged by `expect_source` when given, else by `source`: the batch must
have been committed under exactly that source (none recorded is a mismatch), or
`~homelabnext.lake.errors.BatchSourceMismatch` is raised and nothing is written.
`expect_source` lets a writer re-send a batch without its mark (`source=None`, so the
mark does not move back) and still have it judged as its own; with neither, the replay
is not judged.

<details><summary>Full adapter notes</summary>

Target-file factories for the lake capabilities on real products.

`make_lake` builds a `homelabnext.lake.trino_rest.TrinoRestLake`: queries through the
`lake-query` endpoint (Trino), metadata and the batch ledger through the `lake-catalog`
endpoint (an Iceberg REST catalog such as Lakekeeper).  Both suites, `lake-query` and
`lake-catalog`, need the whole `LakeClient` (they seed through `write_batch` and count
through `query`), so both targets use this one factory.

Every subject of one run shares a scratch namespace `hnx_conform_<run>` (created with the pinned
tables on first use), so a run never sees another run's rows.  Plain `http` is accepted only to
a loopback address unless `allow_plaintext=True` (the same rule as `TrinoLake`).

**Every reader signs in to the engine** (ADR-0033 decision 6: the row filters of
`lake-access.json` are keyed on the session user, so a user named by a bare header would make
every ceiling honour-system).  `credential` is a secret reference (`secret:<name>`, never a
value), delivered in `HNX_SECRET_<NAME>` (`homelabnext.registry.model.secret_env_name`):
the reader's password in the engine's per-reader password file.  The engine client sends it as
HTTP Basic for the reader's login (`homelabnext.lake.trino_http.engine_login`;
`reader_secret` is the conventional name).  `catalog_credential` is a second secret
reference, the catalog's bearer token, when the catalog asks for one.  With a credential, both
clients send through `homelabnext._http.credential_opener` (`ca_file` for a private CA):
no redirect is followed and no proxy is used, so the credential reaches only the endpoint.

**A `lake-query` endpoint that is not loopback is refused without a credential**, outright:
there is no flag that reads a lab's lake unauthenticated.  Only the lab-in-a-box, bound to
loopback, runs without one.  The value is read from its variable when the lake is built (a
missing one fails at once) and again at every request, so no object holds it.
